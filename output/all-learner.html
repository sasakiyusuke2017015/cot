第1章 · frontend

🏗️ HTML

ページの骨組みを作る

🎯 この章のゴール: HTMLが「見た目」ではなく「構造」を書く言語だと理解し、基本のタグでページの骨組みを作れるようになる。

HTMLとは何か

HTML（HyperText Markup Language）は、Webページの構造（骨組み）を記述する言語です。「ここは見出し」「ここは段落」「ここはリスト」と、内容に意味を与えていきます。色や配置などの見た目は次章のCSSが担当します。

要素とタグ

HTMLは「要素」の積み重ねでできています。要素は開始タグと終了タグで内容を挟んで書きます。

<h1>今日の献立</h1>
<p>今日はカレーを作ります。</p>
<ul>
  <li>じゃがいも</li>
  <li>にんじん</li>
  <li>玉ねぎ</li>
</ul>
<a href="https://example.com">レシピを見る</a>

まず覚えるタグ

  • h1〜h6 … 見出し（h1が最上位）
  • p … 段落
  • ul / ol / li … リスト（黒丸 / 番号つき）
  • a … リンク（href属性で行き先を指定）
  • img … 画像（src属性でファイルを指定）
  • div / span … 意味を持たないグループ化の入れ物
💡 コツ: ブラウザで右クリック →「検証」（開発者ツール）を開くと、どんなページもHTMLの構造を見られます。好きなサイトの骨組みを覗いてみるのが一番の教材です。

なぜ「構造」と「見た目」を分けるのか

HTMLには文字を大きくしたり色を付けたりするタグも一応あります。ですが今はほとんど使いません。構造と見た目を混ぜると、後から変更するのが地獄になるからです。

たとえば「見出しの色を全部変えたい」とき、構造と見た目が分かれていればCSSの1行を直すだけで済みます。混ざっていると、全ページの全見出しを手で直すことになります。この分離の恩恵は次章で実感できます。

🛠 課題: プロフィールカード（第1段階）

自分のプロフィールカードをHTMLだけで作ります。この課題は第2章・第3章で育てていくので、消さずに取っておいてください。

作るもの

  1. `profile.html` というファイルを作る
  2. 名前を h1、肩書き（学習中のことなど）を p で書く
  3. 「できること」を ul のリストで3つ以上書く
  4. 好きなサイトへのリンクを a で貼る
  5. ブラウザで開いて表示を確認する

できたと言える条件

ブラウザで開くと内容が表示される
開発者ツールで見たとき、意図した入れ子になっている
なぜその要素を選んだか説明できる（なぜ div ではなく h1 か）

💡 見た目が地味でも気にしないこと。今は「構造が正しいか」だけを見ます。飾りつけは次章の仕事です。

チェックリスト

HTMLの役割は「構造」だと説明できる
開始タグ・終了タグ・属性の書き方が分かる
開発者ツールで他のページの構造を見たことがある
profile.html を作ってブラウザで表示できた

🔑 重要キーワード

HTMLWebページの構造（骨組み）を記述する言語
タグ要素の始まりと終わりを示す目印。<p>〜</p> のように書く
要素タグで挟まれたページの構成単位。見出し・段落など
属性要素に追加する情報。href や src など
開発者ツールブラウザ内蔵の解析ツール。右クリック→検証で開く

📝 確認クイズ

  • ページの構造（骨組み）を記述する
  • ページの見た目を装飾する
  • ページに動きをつける
  • データベースを操作する
答えと解説

正解: ページの構造（骨組み）を記述する

正しくは「ページの構造（骨組み）を記述する」。構造はHTML・見た目はCSS・動きはJavaScriptと役割が分かれている。

Q2. ページ内で最上位の見出しを表すHTMLタグはどれか。

  • p
  • div
  • span
  • h1

正解: h1

第2章 · frontend

🎨 CSS

見た目とレイアウトを整える

🎯 この章のゴール: セレクタでHTML要素を選んでスタイルを当てる仕組みを理解し、Flexboxで簡単なレイアウトを組めるようになる。

CSSとは何か

CSS（Cascading Style Sheets）は、HTMLで作った骨組みに見た目（色・大きさ・配置）を与える言語です。「どの要素に」「どんなスタイルを」の2つをセットで書きます。

/* セレクタ { プロパティ: 値; } */
h1 {
  color: #1e3a8a;
  font-size: 2rem;
}
.card {          /* class="card" の要素に当たる */
  padding: 16px;
  border-radius: 8px;
}

セレクタの基本

  • h1 … タグ名で選ぶ
  • .card … class属性で選ぶ（先頭にドット）。最もよく使う
  • #header … id属性で選ぶ（先頭にシャープ）

ボックスモデル

すべての要素は箱（ボックス）として描画されます。内側から content → padding → border → margin の層になっていて、レイアウト崩れの原因の大半はここの理解不足です。

Flexboxで並べる

.row {
  display: flex;        /* 子要素を横に並べる */
  gap: 12px;            /* 要素間の隙間 */
  justify-content: center;  /* 水平方向の揃え */
  align-items: center;      /* 垂直方向の揃え */
}
💡 コツ: 開発者ツールで要素を選ぶと、ボックスモデル（padding / margin）が色付きで表示されます。「なぜズレるのか」は目で見て確認するのが最短です。

CSSファイルを分ける

CSSはHTMLの中に直接書くこともできますが、別ファイルにして読み込むのが基本です。こう書きます。

<!-- profile.html の <head> の中 -->
<link rel="stylesheet" href="style.css">
📌 なぜ分けるのか: 前章で「構造と見た目を分ける」と言いました。ファイルまで分けると、その恩恵がはっきりします。1つのCSSファイルを複数のページで使い回せるので、サイト全体の見た目を1か所で変えられます。逆にHTMLに直接書くと、ページが増えるたび同じ指定をコピーすることになります。

🛠 課題: プロフィールカード（第2段階 — 見た目を整える）

第1章で作った profile.html に、外部CSSファイルでスタイルを当てます。HTMLファイルは構造だけ、見た目は全部CSSファイル、という分担を体験するのが狙いです。

作るもの

  1. `style.css` を作り、profile.html から link で読み込む
  2. カード風の見た目にする（背景色・padding・border-radius・box-shadow）
  3. 名前と肩書きで文字サイズや色に差をつけ、情報の優先順位を表現する
  4. Flexbox を使って、リストの項目を横並びのタグ風にする
  5. HTMLファイルには style 属性を1つも書かない

できたと言える条件

style.css を削除すると、見た目だけが消えて内容は残る
HTMLに style="..." が1つも書かれていない
開発者ツールでボックスモデルを見て、余白がどこから来ているか説明できる

💡 「HTMLを見て構造が、CSSを見て見た目が分かる」状態が理想です。迷ったら、その要素が「何であるか」はHTML、「どう見えるか」はCSSと考えます。

チェックリスト

セレクタとプロパティの書き方が分かる
ボックスモデルの4層を言える
display:flex で要素を横に並べられる
CSSを別ファイルに分ける理由を説明できる

🔑 重要キーワード

CSSHTMLに見た目（色・大きさ・配置）を与える言語
セレクタスタイルを当てる対象を選ぶ書き方。.card や h1 など
ボックスモデルcontent→padding→border→margin の4層構造
Flexbox要素を柔軟に並べるレイアウト機能。display:flex
開発者ツール要素のボックスモデルを色付きで確認できる

📝 確認クイズ

Q1. class属性が「card」の要素を選ぶCSSセレクタはどれか。

  • .card
  • #card
  • card()
  • @card
答えと解説

正解: .card

classはドット（.card）で選ぶ。#はid用のセレクタであり関数形や@形式のセレクタは存在しない。

Q2. 子要素を横一列に並べたいとき親要素に指定するCSSはどれか。

  • color: red;
  • font-size: 2rem;
  • content: row;
  • display: flex;
答えと解説

正解: display: flex;

「display: flex;」を親要素に指定すると子要素が横に並びgapやjustify-contentで整えられる。

第3章 · frontend

⚡ JavaScript

ページに動きをつける

🎯 この章のゴール: 変数・条件分岐・繰り返し・関数・配列を使えるようになり、ボタンクリックでページが変わる体験をする。

JavaScriptとは何か

JavaScriptは、ページに動き（ロジック）を与えるプログラミング言語です。「ボタンを押したら表示を変える」「入力内容をチェックする」など、ユーザーの操作に反応する部分を担当します。

基本文法

const name = '田中';            // 変数（再代入しないなら const）
let count = 0;                  // 再代入するなら let

if (count > 10) {               // 条件分岐
  console.log('多いですね');
} else {
  console.log('まだ少ない');
}

const fruits = ['りんご', 'みかん', 'バナナ'];  // 配列
for (const f of fruits) {       // 繰り返し
  console.log(f);
}

function greet(who) {           // 関数
  return 'こんにちは、' + who + 'さん';
}

DOM操作 — HTMLとつなぐ

const btn = document.querySelector('#myButton');
btn.addEventListener('click', () => {
  document.querySelector('#message').textContent = '押されました！';
});
⚠️ ここが本番: JavaScriptからは必ずエラーに出会います。エラーが出たら「エラー文を読む → 原因の仮説を立てる → 調べる → 修正する」。この流れを毎回意識してください。エラー文はコンソール（開発者ツールのConsoleタブ）に出ます。
💡 コツ: 困ったらまず console.log() で変数の中身を表示して確認する癖をつけましょう。「思っていた値と違う」がバグの正体であることがほとんどです。

JSファイルも分ける

CSSと同じで、JavaScriptも別ファイルにします。`</body>` の直前で読み込むのが基本です。

<!-- profile.html の </body> の直前 -->
<script src="script.js"></script>
📌 3つの役割がそろった: これで HTML（構造）・CSS（見た目）・JavaScript（動き） の3ファイル構成になります。この分け方はWeb開発の基本形で、どんな大きなサイトも根っこは同じです。「どのファイルを直せばいいか」が明確になるのが最大の利点です。

🛠 課題: プロフィールカード（第3段階 — 動かす）

第2章までのカードに動きをつけます。3つのファイルがそれぞれ何を担当しているかを、自分の言葉で説明できるようになるのが本当のゴールです。

作るもの

  1. `script.js` を作り、profile.html から読み込む
  2. 「詳細を見る」ボタンを置き、押すと隠れていた自己紹介文が表示されるようにする
  3. もう一度押すと隠れる（トグル）ようにする
  4. 「いいね」ボタンを作り、押すたびに数が増えるようにする
  5. 押した回数が10を超えたら、メッセージを変える

できたと言える条件

ボタンを押すと表示が変わる
script.js を読み込まなくしても、ページ自体は壊れずに表示される
HTML・CSS・JS がそれぞれ何をしているか説明できる

💡 表示・非表示は CSS のクラスを付け外しする方法（classList.toggle）が定石です。JSから直接スタイルをいじるより、CSSに定義したクラスを切り替えるほうが後から変更しやすくなります。

💡 次章への橋渡し: ここまでで HTML・CSS・JavaScript がそろい、「動くWebページ」を自力で作れる状態になりました。次章ではGitを覚えて、いよいよ2人でオセロを作ります。実はオセロは、ここまでの知識だけで作れます。

チェックリスト

const と let の使い分けが分かる
if / for / 関数 / 配列を組み合わせて書ける
エラーが出たらコンソールを読む習慣がある
HTML / CSS / JS の3ファイル構成でページを作れた

🔑 重要キーワード

変数値に名前を付けて保存する。const（再代入不可）と let
条件分岐if / else で条件に応じて処理を切り替える
配列複数の値を順番に持つ入れ物。length で要素数
DOM操作JavaScriptからHTML要素を取得・変更すること
console.log変数の中身をコンソールに表示するデバッグの基本

📝 確認クイズ

Q1. JavaScriptの主な役割はどれか。

  • ページに動き（ロジック）をつける
  • ページの構造を定義する

第4章 · vcs

🌿 Git

コードの履歴を管理する

🎯 この章のゴール: 「保存のたびに履歴が残る」感覚を身につけ、5つの基本コマンドで自分のコードをGitHubに置けるようになる。

なぜ今Gitを学ぶのか

Gitはコードの変更履歴を記録する道具です。TypeScriptやReactより先に学ぶのは、実際の開発では早い段階からGitを使う習慣をつけたほうが自然だからです。ここから先の演習はすべてGitで履歴を残しながら進めます。

まず覚える5コマンド

git clone <URL>     # リモートのリポジトリを手元に複製する
git add .           # 変更をステージに載せる（コミット対象にする）
git commit -m "メッセージ"   # 変更を履歴として記録する
git push            # 手元の履歴をGitHubに送る
git pull            # GitHubの最新を手元に取り込む

日々の流れは「書く → add → commit → push」の繰り返しです。この5つだけで十分。branchやrebaseは後回しで構いません（チーム開発に入る段階で学びます）。

💡 コツ: commitメッセージは「何をしたか」を短く書きます（例:「カウンター機能を追加」）。1日の終わりにまとめて1回ではなく、キリのいい単位でこまめにcommitするのがおすすめです。
⚠️ 注意: パスワードやAPIキーを書いたファイルをcommitしないこと。一度pushした履歴は簡単には消せません。秘密情報は .gitignore で除外します。

✏️ 演習

GitHubにリポジトリを作り、前章までの自己紹介ページとカウンターをpushしてみましょう。3回以上commitを分けて、GitHub上で履歴が見えることを確認します。

チェックリスト

clone / add / commit / push / pull の役割を言える
自分のコードをGitHubにpushできる
こまめにcommitする習慣がついている

🔑 重要キーワード

リポジトリコードと履歴をまとめて管理する保管庫
commit変更を履歴として記録する操作
push / pull手元の履歴をGitHubへ送る / 最新を取り込む
GitHubリポジトリをネット上に置いて共有するサービス
.gitignore履歴に含めないファイルを指定する設定

📝 確認クイズ

Q1. git commitが行うことはどれか。

  • 変更を履歴として記録する
  • ファイルを削除する
  • コードを自動で修正する
  • サーバーにアプリを公開する
答えと解説

正解: 変更を履歴として記録する

commitは「この時点の変更」を履歴として記録する操作でありpushでその履歴をGitHubに送る。

Q2. 学習の最初の段階で覚えるべきGitコマンドの組み合わせはどれか。

  • rebase・cherry-pick・stash
  • merge・tag・bisect
  • reset・revert・reflog
  • clone・add・commit・push・pull
答えと解説

正解: clone・add・commit・push・pull

最初は基本5コマンド（clone・add・commit・push・pull）で十分でありbranchやrebaseはチーム開発に入る段階で学べばよい。

第5章 · 発展

🔷 TypeScript

型でコードを安全にする

🎯 この章のゴール: 「型があると実行する前に間違いに気付ける」価値を体感し、基本の型注釈とinterfaceを書けるようになる。

TypeScriptとは何か

TypeScriptは、JavaScriptに型を追加した言語です。書いたコードはJavaScriptに変換されて動きます。つまり「JavaScriptの上位互換」で、これまで学んだ文法はそのまま使えます。

型注釈の基本

let count: number = 0;
let name: string = '田中';
let done: boolean = false;
let tags: string[] = ['html', 'css'];

function add(a: number, b: number): number {
  return a + b;
}

add(1, 2);      // OK
add('1', '2');  // ← 実行する前にエラーで教えてくれる！

interface — データの形を決める

interface User {
  id: number;
  name: string;
  email: string;
}

function showUser(user: User) {
  console.log(user.name);
  console.log(user.mail);  // ← 「mailは存在しない」と教えてくれる
}
📌 なぜ型が大事か: JavaScriptだけだと、間違いは実行して初めて分かります。TypeScriptなら書いた瞬間にエディタが教えてくれる。バグ探しの時間が大幅に減り、あとで学ぶReactやAPI連携でも「データの形」が明確になります。
💡 コツ: VS Codeで赤い波線が出たらマウスを乗せてエラーメッセージを読む。TypeScriptのエラー文は最初は長く感じますが「何が」「どの型と」合わないかが必ず書いてあります。

✏️ 演習

カウンターのコードをTypeScriptに書き換えてみましょう。さらに User interface を定義して、ユーザーの配列から名前一覧を表示する関数を書きます。

チェックリスト

number / string / boolean / 配列の型注釈が書ける
interfaceでデータの形を定義できる
エディタの型エラーを読んで直せる

🔑 重要キーワード

TypeScriptJavaScriptに型を追加した言語。JSに変換されて動く
型注釈変数や引数に「: number」のように型を書くこと
interfaceオブジェクト（データ）の形を定義する仕組み
コンパイルTypeScriptをJavaScriptに変換すること
型エラー型が合わないときにエディタが出す警告。実行前に気付ける

📝 確認クイズ

Q1. TypeScriptの説明として正しいものはどれか。

  • JavaScriptに型を追加した言語でJavaScriptに変換されて動く
  • JavaScriptとは無関係の全く新しい言語
  • HTMLの新しいバージョン
  • データベース専用の言語
答えと解説

正解: JavaScriptに型を追加した言語でJavaScriptに変換されて動く

TypeScriptはJavaScriptの上位互換でありコンパイルするとJavaScriptになるため既存の知識がそのまま活きる。

Q2. 型注釈がある一番の利点はどれか。

  • コードの実行速度が2倍になる
  • デザインが自動で良くなる
  • サーバー代が安くなる
  • 実行する前に間違いに気付ける
答えと解説

正解: 実行する前に間違いに気付ける

型があるとエディタが書いた瞬間に間違いを指摘してくれるため実行して初めてバグに気付くことが減る。

⚛️ React

画面を部品で組み立てる

🎯 この章のゴール: コンポーネント・props・state の3つを理解し、部品を組み合わせて画面を作れるようになる。

Reactとは何か

Reactは、画面をコンポーネント（部品）として分割して組み立てるライブラリです。「ボタン」「カード」「一覧」を部品として作り、組み合わせて画面にします。部品は再利用できるので、大きなアプリでも整理された状態を保てます。

コンポーネントとJSX

function Hello(props) {
  return <h1>こんにちは、{props.name}さん</h1>;
}

function App() {
  return (
    <div>
      <Hello name="田中" />
      <Hello name="佐藤" />
    </div>
  );
}

HTMLに似た書き方（JSX）でコンポーネントの見た目を書きます。propsは部品に渡すデータです。同じ部品でも渡すpropsを変えれば表示が変わります。

state — 画面が変わる仕組み

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      {count} 回押しました
    </button>
  );
}
📌 Reactの考え方: DOMを直接書き換えるのではなく、stateを変えると画面が自動で再描画される。「画面 = stateの反映結果」と考えるのがReactの核心です。
💡 コツ: 迷ったら「この画面はどんな部品に分けられるか？」から考えます。ヘッダー・一覧・一覧の1行・ボタン…と分解してから作り始めると設計が楽になります。

第7章 · backend

🔌 API

データをやり取りする窓口

🎯 この章のゴール: フロントエンドとサーバーがHTTPとJSONでやり取りする仕組みを理解し、fetchでAPIを呼び、簡単なAPIを自作できるようになる。

APIとは何か

API（Application Programming Interface）は、プログラム同士がデータをやり取りする窓口です。Reactで作った画面（フロントエンド）は、APIを通じてサーバーからデータをもらい、サーバーにデータを送ります。

[ブラウザ / React]  ←── HTTP + JSON ──→  [サーバー / API]

GET  /api/todos      … 一覧が欲しい
POST /api/todos      … 新しく追加したい
PUT  /api/todos/1    … 1番を更新したい
DELETE /api/todos/1  … 1番を削除したい

JSONとfetch

やり取りするデータはJSONという形式で書きます。JavaScriptからAPIを呼ぶには fetch を使います。

// APIからデータを取得して表示する
const res = await fetch('/api/todos');
const todos = await res.json();
// → [{ "id": 1, "title": "牛乳を買う", "done": false }, ...]

// APIにデータを送る
await fetch('/api/todos', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: '掃除をする' }),
});

自分でAPIを作る（Node.js）

import express from 'express';
const app = express();
app.use(express.json());

const todos = [{ id: 1, title: '牛乳を買う', done: false }];

app.get('/api/todos', (req, res) => {
  res.json(todos);
});

app.listen(3000);
💡 コツ: 開発者ツールのNetworkタブを開くと、ページが実際にどんなAPIを呼んでいるか全部見えます。うまく動かないときは「リクエストは飛んだか」「何が返ってきたか」をここで確認します。

第8章 · backend

🗄️ DB

データの保存先を知る

🎯 この章のゴール: データベースの役割とSQLの基本4操作を理解し、「APIがアプリとDBの橋渡しをしている」全体像をつかむ。

なぜデータベースが要るのか

前章のAPIは、データを変数（メモリ）に持っていたため、サーバーを再起動すると消えてしまいます。データを永続的に保存する場所がデータベース（DB）です。

[React] ←→ [API / Node.js] ←→ [DB / PostgreSQLなど]
 画面        橋渡し・入り口       データの保存先

この3層の絵が、Webアプリの基本形です。APIがアプリとDBの橋渡しをしている、と理解できればこの章の半分は達成です。

テーブルとSQL

リレーショナルDBでは、データをExcelのようなテーブル（表）で管理します。操作にはSQLという言語を使います。

-- 取得（Read）
SELECT * FROM todos WHERE done = false;

-- 追加（Create）
INSERT INTO todos (title, done) VALUES ('牛乳を買う', false);

-- 更新（Update）
UPDATE todos SET done = true WHERE id = 1;

-- 削除（Delete）
DELETE FROM todos WHERE id = 1;

この4操作をまとめてCRUD（Create / Read / Update / Delete）と呼びます。APIのGET / POST / PUT / DELETEときれいに対応します。

ORM — コードからDBを扱う

// ORM（例: Prisma）を使うとSQLをコードで書ける
const todos = await prisma.todo.findMany({ where: { done: false } });
await prisma.todo.create({ data: { title: '牛乳を買う' } });

ORMを使うとTypeScriptの型とDBがつながり、安全にデータを扱えます。まずはSQLで仕組みを理解してからORMに進むのがおすすめです。

⚠️ 注意: ユーザーの入力をそのままSQL文字列に埋め込むと、SQLインジェクションという攻撃を受けます。必ずプレースホルダやORMを使いましょう。

第9章 · release

🚀 デプロイ

世界に公開する

🎯 この章のゴール: 自分の作ったWebアプリをインターネットに公開し、「自分でWebサービスを作った」を実感する。

デプロイとは何か

デプロイとは、手元で動いているアプリをインターネット上のサーバーに配置して、誰でも使える状態にすることです。ここまで学んだ全部の総仕上げです。

コードを書く
   ↓
GitHubへ push
   ↓
ホスティングサービスが自動でビルド・公開
   ↓
https://あなたのアプリ.vercel.app  ← 世界中からアクセスできる

今どきのデプロイはGit連携

VercelやNetlify、Render などのホスティングサービスは、GitHubのリポジトリを連携するだけで、pushのたびに自動で最新版を公開してくれます。第4章で身につけたGitの習慣がここで直接活きます。

  • フロントエンド（React）… Vercel / Netlify などが定番
  • API + DB … Render / Railway など、DBも一緒に提供するサービスが手軽
⚠️ 公開前チェック: APIキーやパスワードを環境変数にしたか。誰でも触れる状態になるので、秘密情報がコードに残っていないか必ず確認します。
💡 なぜデプロイが大事か: 公開URLを人に送って使ってもらえると、学習のモチベーションが一気に変わります。「動くものを世界に出した」経験が、次の学習の最大の燃料になります。
