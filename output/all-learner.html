🏗️ HTML

ページの骨組みを作る

🎯 この章のゴール: HTMLが「見た目」ではなく「構造」を書く言語だと理解し、意味に合ったタグを選んでページの骨組みを作れるようになる。最終的にオセロの盤面もHTMLで組みます。

はじめに — 道具をそろえる

本題に入る前に、開発に使う道具を用意します。ここは一度やれば以降ずっと使うものなので、面倒でも最初にきちんと整えてください。必要なのは「エディタ」と「ブラウザ」の2つだけです。

① VS Code を入れる

コードを書くための専用エディタです。メモ帳でも書けますが、色分け・入力補完・エラー表示があるかどうかで学習効率がまるで変わります。現場で最も使われているエディタでもあります。

  1. Visual Studio Code で検索し、公式サイトからダウンロードする（無料）
  2. インストーラを実行する。選択肢はすべて既定のままでよい
  3. 起動して、真っ黒な画面が出れば成功

起動したら、拡張機能を入れます。左側の四角が4つ並んだアイコン（Extensions）をクリックし、名前で検索してインストールしてください。

拡張機能何ができるか必須度
Japanese Language PackVS Code のメニューが日本語になる好みで
Live Server保存すると自動でブラウザが更新されるほぼ必須
HTML CSS SupportHTMLの中でCSSクラス名を補完してくれるあると楽
📌 Live Server がいちばん効く: これを入れると、HTMLファイルを右クリック →「Open with Live Server」で開けます。以降はファイルを保存するだけでブラウザが自動更新されるので、「保存 → ブラウザに切り替え → 再読み込み」の繰り返しが不要になります。地味ですが学習速度がかなり変わります。

② 作業フォルダを作る

作ったファイルが散らからないよう、専用のフォルダを決めます。日本語やスペースを含まない場所にするのが無難です（後々ツールが誤動作する原因になります）。

C:\dev\web-study\          ← ここを作業フォルダにする
  ├─ profile.html          ← 第1章で作る
  ├─ style.css             ← 第2章で追加
  └─ script.js             ← 第3章で追加

フォルダを作ったら、VS Code の「ファイル → フォルダーを開く」でそのフォルダを開いてください。左側にファイル一覧が出れば準備完了です。

⚠️ 拡張子を表示させておく: Windowsは初期設定で拡張子（.html などの末尾）を隠します。この状態で作業すると
「profile.html」のつもりが「profile.html.txt」になっていて開けないという事故が起きます。

エクスプローラーの「表示」タブ →「ファイル名拡張子」にチェックを入れて、必ず表示させてください。

③ ブラウザと開発者ツール

ブラウザは Chrome か Edge を使ってください。どちらも同じ仕組みで動いており、開発者向けの機能が充実しています。

準備できたら、いま見ているこのページで F12キー を押してみてください。画面が分割されて、コードのようなものが出れば成功です。これが開発者ツールで、この先ずっと使います（詳しい使い方はこの章の後半で説明します）。

💡 これで準備完了: 道具はこれだけです。Web開発は最初の一歩の敷居が低いのが良いところで、エディタとブラウザさえあれば始められます。Gitやサーバは必要になったときに入れます（第4章・第5章）。

そもそもWebページとは何でできているか

普段見ているWebページは、実はただのテキストファイルです。ブラウザがそのテキストを読んで、解釈して、画面に描いています。魔法は何もありません。

そのテキストは3種類の役割に分かれています。この分担がWeb開発の土台なので、最初に頭に入れてください。

言語役割例えるなら
HTML構造（何がどこにあるか）家の骨組み・間取り
CSS見た目（どう見えるか）内装・壁紙・家具の配置
JavaScript動き（何が起きるか）電気・水道などの設備

この章で扱うのはHTMLだけです。見た目が地味でも気にしないでください。骨組みが正しくできていれば、あとから内装はいくらでも変えられます。

最小のHTMLファイル

まずは動くものを見ます。テキストエディタで次を書いて index.html という名前で保存し、ダブルクリックしてブラウザで開いてください。

<!DOCTYPE html>
<html lang="ja">
  <head>
    <meta charset="UTF-8">
    <title>はじめてのページ</title>
  </head>
  <body>
    <h1>こんにちは</h1>
    <p>これが最初のWebページです。</p>
  </body>
</html>

表示されましたか。これでもうWebページを作ったことになります。順に何を書いたか見ていきます。

  • <!DOCTYPE html> … 「これはHTMLです」という宣言。おまじないと思ってよい。必ず1行目に書く
  • <html lang="ja"> … 全体を包む要素。lang="ja" は日本語のページだという情報
  • <head> … ページの設定を書く場所。画面には表示されない
  • <meta charset="UTF-8"> … 文字コードの指定。これが無いと日本語が文字化けする
  • <title> … ブラウザのタブに出る名前
  • <body> … 実際に画面に表示される中身。ここが本体
⚠️ 文字化けしたら: 日本語が「譁�蟄怜喧縺�」のように壊れて見えたら、ほぼ <meta charset="UTF-8"> の書き忘れです。ファイル自体の保存形式がUTF-8になっているかも確認してください（VS Codeなら右下に表示されます）。

要素とタグ — HTMLの基本単位

HTMLは要素の積み重ねでできています。要素は「開始タグ」「中身」「終了タグ」の3つで1組です。

<p>これが段落です。</p>
↑            ↑        ↑
開始タグ     中身     終了タグ（/ が付く）

終了タグを忘れると、そこから後ろが全部おかしくなります。慣れるまでは開始タグを書いたらすぐ終了タグも書いて、後から中身を埋めるやり方が安全です。

入れ子（ネスト）— 箱の中に箱を入れる

要素の中に別の要素を入れられます。これを入れ子と呼びます。HTMLの構造はすべてこの入れ子でできています。

<ul>
  <li>じゃがいも</li>
  <li>にんじん</li>
  <li>玉ねぎ</li>
</ul>
⚠️ 閉じる順番は「後に開けたものを先に閉じる」: 箱を入れ子にするのと同じで、順番を守らないと壊れます。

⭕ 正しい: <p>これは<strong>大事</strong>です</p>
❌ 誤り: <p>これは<strong>大事</p></strong>

💡 インデントを付ける: 入れ子になったら、中の要素は半角スペース2つ分ずらして書きます。ブラウザの動作には影響しませんが、人間が読むときに構造が一目で分かります。これは実務でも必ず守られている習慣です。

属性 — 要素に情報を足す

タグには属性という追加情報を書けます。「開始タグの中に、名前=\"値\" の形で書く」と覚えてください。

<a href="https://example.com">リンクの文字</a>
   ↑    ↑
   属性名 値（ダブルクォートで囲む）

<img src="cat.jpg" alt="猫の写真">
<div id="board" class="game-area">…</div>
属性使うタグ意味
hrefaリンク先のURL
srcimg画像ファイルの場所
altimg画像が表示できないときの代替文。読み上げにも使われる
idどの要素にもその要素だけの名前。ページ内で重複させない
classどの要素にもグループ名。同じclassを複数の要素に付けてよい
📌 id と class は後で効いてくる: いまは「名前を付けるもの」という理解で十分です。ただし次章のCSSと第3章のJavaScriptで多用します。CSSは「この名前の要素をこう見せる」、JavaScriptは「この名前の要素を操作する」ために使います。ここで名前を付ける習慣をつけておくと後が楽です。

まず覚えるタグ

HTMLのタグは100種類以上ありますが、実際によく使うのは20個程度です。まずは次のものから覚えてください。

タグ意味補足
h1〜h6見出しh1が最上位。1ページにh1は1つが基本
p段落文章のかたまり
ul / li順序なしリスト黒丸のリスト。liはulの中にだけ書く
ol / li順序つきリスト番号が振られる
aリンクhref属性で行き先を指定
img画像終了タグが無い（中身を持たないため）
table表オセロの盤面にも使える
buttonボタン押せる要素。JSと組み合わせる
input入力欄終了タグが無い
div意味を持たない箱グループ化のための入れ物
span意味を持たない箱（文中用）文章の一部を囲むとき

div と span の違い

初心者がよく混乱する2つです。役割は同じ「意味を持たない箱」ですが、表示のされ方が違います。

  • div … 前後で改行される（縦に積まれる）。ブロック要素と呼ぶ
  • span … 改行されず、文章の中に収まる。インライン要素と呼ぶ
<div>これは箱1</div>
<div>これは箱2</div>
<!-- → 縦に2段で表示される -->

<p>この文の<span>ここだけ</span>を囲む</p>
<!-- → 1行のまま。spanは流れを乱さない -->

「見た目」でタグを選んではいけない

ここがこの章でいちばん大事な話です。「文字を大きくしたいからh1を使う」という選び方をしないでください。h1は「このページの主題」を表すタグであって、文字を大きくするタグではありません。

❌ 悪い例（見た目で選んでいる）
<h1>会社概要</h1>
<h1>お問い合わせ</h1>     ← 大きくしたいから h1 にした

⭕ 良い例（意味で選んでいる）
<h1>株式会社サンプル</h1>  ← ページの主題は1つ
<h2>会社概要</h2>
<h2>お問い合わせ</h2>

意味に合ったタグを選ぶことをセマンティックなHTMLと言います。なぜ大事かというと、HTMLを読むのは人間の目だけではないからです。

  • 検索エンジン … h1やタグ構造を見てページの内容を理解する。検索結果での見え方が変わる
  • スクリーンリーダー … 目の不自由な人が使う読み上げソフト。「見出しだけ拾って移動」ができるのは h1〜h6 が正しく付いているページだけ
  • あとで直す人 … 下の例を見てください

3つ目が分かりにくいので、具体例を出します。次の2つは画面上はまったく同じに見えます。半年後にこのコードを開いて、どこを直せばいいか分かるのはどちらでしょうか。

❌ 全部 div で書いた場合
<div class="t1">料金プラン</div>
<div class="b1">
  <div class="t2">無料プラン</div>
  <div class="x">月0円</div>
</div>

⭕ 意味のあるタグで書いた場合
<h2>料金プラン</h2>
<section>
  <h3>無料プラン</h3>
  <p>月0円</p>
</section>

上は t1 b1 x が何なのか、CSSを開いて照らし合わせないと分かりません。下は読むだけで「料金プランの見出しがあって、その下に無料プランの説明がある」と分かります。半年後の自分は他人です。そのとき助かるのは下の書き方です。

💡 判断に迷ったときの問い: 「CSSを全部外したとき、この文書は読めるか」を考えてみてください。見出し・段落・リストが適切なら、装飾ゼロでも意味が通ります。通らないなら、タグの選び方を見直す合図です。

なぜ「構造」と「見た目」を分けるのか

実はHTMLにも文字を大きくしたり色を変えたりするタグ（<font> など）が存在します。ですがもう使われません。構造と見た目を混ぜると、後から変更するのが地獄になるからです。

例えば100ページのサイトで「見出しの色を変えたい」となったとき——構造と見た目が分かれていればCSSの1行を直すだけで全ページに反映されます。混ざっていると、100ページ分の全見出しを手作業で直すことになります。この差は決定的です。

開発者ツールを開いてみる

ブラウザには、表示中のページのHTMLを見る機能が標準で付いています。世の中の全Webページが教材になるので、必ず使えるようになってください。

  1. 好きなWebページを開く
  2. 気になる部分を右クリック →「検証」（または F12）
  3. 画面が分割され、そのページのHTMLが表示される
  4. HTMLの行にマウスを乗せると、画面上の対応する場所が光る
💡 使い方のコツ: 「このボタン、どう作られているんだろう」と思ったら右クリック→検証。プロが書いたHTMLをいくらでも読めます。最初は複雑で面食らいますが、知っているタグを探すだけでも勉強になります。

🛠 課題: プロフィールカード（第1段階）

自分のプロフィールカードをHTMLだけで作ります。この課題は第2章・第3章で育てていくので、消さずに取っておいてください。見た目は次章で整えるので、いまは構造だけに集中します。

作るもの

  1. profile.html を作り、DOCTYPE から body までの骨組みを書く
  2. タブに表示される title を自分の名前にする
  3. 名前を h1、肩書き（学習中のことなど）を p で書く
  4. 「できること」を ul のリストで3つ以上書く
  5. 好きなサイトへのリンクを a で貼る（新しいタブで開く方法も調べてみる）
  6. 自己紹介文を p で2〜3段落書く
  7. 各パーツを div で囲み、id か class で名前を付けておく（次章で使う）
  8. ブラウザで開いて表示を確認し、開発者ツールで構造を見る

ブラウザで開くと内容が表示される

文字化けしていない
h1 が1つだけになっている

📝 確認クイズ

Q1. HTMLの役割として最も適切なものはどれか。

  • ページの構造（骨組み）を記述する
  • ページの見た目を装飾する
  • ページに動きをつける
  • データベースを操作する
答えと解説

正解: ページの構造（骨組み）を記述する

正しくは「ページの構造（骨組み）を記述する」。構造はHTML・見た目はCSS・動きはJavaScriptと役割が分かれている。

Q2. ページ内で最上位の見出しを表すHTMLタグはどれか。

  • p
  • div
  • span
  • h1
答えと解説

正解: h1

見出しはh1〜h6で表しh1が最上位。1ページにh1は1つが基本である。pは段落・div/spanは意味を持たないグループ化の入れ物。

Q3. 次のうち、入れ子の閉じ方が正しいものはどれか。

  • <p>これは<strong>大事です</p>
  • <strong><p>これは大事</strong></p>
  • <p>これは<strong>大事</strong>です</p>
  • <p>これは<strong>大事</p></strong>
答えと解説

正解: <p>これは<strong>大事</strong>です</p>

入れ子は「後に開けたものを先に閉じる」のが原則。順番が入れ替わると表示が崩れる原因になる。

Q4. div と span の違いとして正しいものはどれか。

  • divは見出し用、spanは段落用である

答えと解説

正解: divは前後で改行されるが、spanは文章の流れの中に収まる

divはブロック要素で縦に積まれ、spanはインライン要素で改行されない。どちらも意味を持たない入れ物という点は同じ。

🎨 CSS

見た目とレイアウトを整える

🎯 この章のゴール: セレクタでHTML要素を選んでスタイルを当てる仕組みを理解し、FlexboxとGridでレイアウトを組めるようになる。HTMLを一切変えずに見た目だけを変えられることを体験します。

CSSとは何か

CSS（Cascading Style Sheets）は、HTMLで作った骨組みに見た目（色・大きさ・配置）を与える言語です。前章で作ったページは真っ白で味気なかったはずですが、HTMLは一行も変えずに見違えるようにできます。

書き方はいたって単純で、「どの要素に」「何を」「どうする」の3つを並べるだけです。

セレクタ {
  プロパティ: 値;
}

/* 実例 */
h1 {
  color: #1e3a8a;      /* 文字色を紺色に */
  font-size: 2rem;     /* 文字の大きさを2倍に */
}
  • セレクタ … どの要素に当てるか（h1、.card など）
  • プロパティ … 何を変えるか（color、font-size など）
  • 値 … どうするか（#1e3a8a、2rem など）
  • 行の終わりには必ずセミコロン ; を付ける
  • /* */ で囲むとコメント（メモ書き）になる

CSSファイルを分けて読み込む

CSSはHTMLの中に直接書くこともできますが、別ファイルにするのが基本です。まず style.css を作り、HTMLの <head> の中で読み込みます。

<!-- profile.html の <head> の中に書く -->
<link rel="stylesheet" href="style.css">
📌 なぜ分けるのか: 前章で「構造と見た目を分ける」と言いました。ファイルまで分けると恩恵がはっきりします。1つのCSSファイルを複数ページで使い回せるので、サイト全体の見た目を1か所で変えられます。HTMLに直接書くと、ページが増えるたび同じ指定をコピーすることになります。

セレクタ — どれを選ぶか

セレクタには種類があります。まずは次の3つを覚えてください。

書き方何を選ぶか使いどころ
h1そのタグ全部「見出しは全部この色」など全体の方針
.cardclass="card" の要素最もよく使う。同じ見た目を複数に当てる
#boardid="board" の要素ページに1つしかないものを狙う
/* タグで選ぶ */
p { line-height: 1.8; }

/* class で選ぶ（先頭にドット） */
.card { background: white; }

/* id で選ぶ（先頭にシャープ） */
#board { width: 400px; }
💡 迷ったら class を使う: idは1ページに1つしか使えず、あとで「他にも同じ見た目にしたい」となったとき困ります。基本はclass、本当に唯一のものだけidと考えておけば失敗しません。

次のHTMLに対して、HTMLを変えずにCSSだけで以下を実現してください。
<h2 class="name">田中</h2> / <p class="role">エンジニア</p> / <p class="role" id="main">リーダー</p>

① すべての p の行間を 1.8 にする
② .role の文字色をグレーにする
③ #main だけ文字を太字にする

確かめ方: 開発者ツールで「リーダー」を選び、3つの指定が全部当たっていることを見る。.role の指定が #main に負けていないのはなぜか、言葉にしてみてください。

組み合わせて絞り込む

セレクタは組み合わせられます。これを知っていると「同じclass名でも場所によって見た目を変える」ことができます。

/* .card の中にある h2 だけ */
.card h2 { color: navy; }

/* card と large の両方を持つ要素 */
.card.large { font-size: 1.5rem; }

/* 複数まとめて同じ指定 */
h1, h2, h3 { font-family: sans-serif; }

詳細度 — 指定がぶつかったらどうなるか

同じ要素に複数の指定が当たると、より具体的なほうが勝ちます。これを詳細度と言います。CSSが効かないときの原因の多くがこれです。

p { color: black; }        /* 弱い */
.intro { color: blue; }    /* こちらが勝つ */
#main { color: red; }      /* さらに強い */

<p class="intro" id="main">この文字は赤になる</p>
  • id（#）… いちばん強い
  • class（.）… 中くらい
  • タグ名（p, h1）… いちばん弱い
  • 同じ強さなら後に書いたほうが勝つ
⚠️ CSSが効かないときの3大原因: ① セレクタが間違っている（class名のタイプミス、ドットの付け忘れ）
② 詳細度で別の指定に負けている
③ そもそもCSSファイルが読み込まれていない

開発者ツールで要素を選ぶと、当たっているCSSと打ち消されたCSS（取り消し線が付く）が見えます。 想像で直さず、まずここを見てください。

ボックスモデル — すべての要素は箱

レイアウトを理解する上で最重要の概念です。すべての要素は4層構造の箱として描画されます。

┌─────────────────────────┐
│  margin（外側の余白）      │
│ ┌─────────────────────┐ │
│ │ border（枠線）         │ │
│ │ ┌─────────────────┐ │ │
│ │ │ padding（内側の余白）│ │ │
│ │ │ ┌─────────────┐ │ │ │
│ │ │ │  content     │ │ │ │
│ │ │ │  （中身）     │ │ │ │
│ │ │ └─────────────┘ │ │ │
│ │ └─────────────────┘ │ │
│ └─────────────────────┘ │
└─────────────────────────┘
層意味使い分け
content文字や画像そのものwidth / height で大きさを指定
padding枠線の内側の余白「箱の中で中身を窮屈にしたくない」とき
border枠線見た目の区切り
margin枠線の外側の余白「隣の要素と離したい」とき
📌 padding と margin の使い分け: 迷ったらこう考えてください。背景色を付けたときに色が付く範囲を広げたいなら padding、要素同士の距離を空けたいなら margin です。paddingは箱の内側なので背景色が付き、marginは外側なので付きません。
.card {
  padding: 16px;              /* 上下左右すべて */
  padding: 16px 24px;         /* 上下 / 左右 */
  padding: 8px 16px 24px 32px; /* 上 右 下 左（時計回り） */

  margin: 0 auto;             /* 上下0、左右autoで中央寄せ */
}
💡 box-sizing は最初に書く: 既定では width に padding と border が含まれません。width:100px に padding:16px を足すと実際は132pxになり、計算が狂います。次の1行を最初に書いておくと、widthが見た目の幅そのものになって直感的です。

* { box-sizing: border-box; }

✏️ ミニ演習③ 余白を当てる（10分）

2枚のカードを縦に並べ、次の見た目を作ってください。開発者ツールのボックスモデル図（Computedタブの色付きの箱）を見ながら進めるのがコツです。

① カードの中の文字が枠から16px離れている
② カード同士が24px離れている
③ カードの背景色を付けたとき、①の余白には色が付き、②の余白には付かない

確かめ方: ①と②のどちらに padding を使い、どちらに margin を使ったか。③がその答え合わせになります。逆にすると③が成立しません。

追加で試す: box-sizing: border-box; の行を消すと、幅を指定したカードがどう変わりますか。消した状態で開発者ツールの幅の数字を見てください。

Flexbox — 一列に並べる

要素を横や縦に並べたいときはFlexboxを使います。並べたい要素の「親」に指定するのがポイントです。

<!-- HTML -->
<div class="row">
  <div>A</div>
  <div>B</div>
  <div>C</div>
</div>
/* CSS：親に指定する */
.row {
  display: flex;              /* 子要素を横に並べる */
  gap: 12px;                  /* 要素の間隔 */
  justify-content: center;    /* 横方向の揃え */
  align-items: center;        /* 縦方向の揃え */
}
プロパティよく使う値効果
flex-directionrow / column横並び / 縦並び
gap8px など要素同士の間隔
justify-contentcenter / space-between並び方向の揃え
align-itemscenter / stretch交差方向の揃え
flex-wrapwrap入りきらないとき折り返す

✏️ ミニ演習④ よくある3つの並びを作る（15分）

<div class="row"> の中にボタンを3つ入れ、CSSだけを書き換えて次の3パターンを順に作ってください。毎回HTMLは同じままです。

① 3つが左端に寄って、間隔が8px空いている
② 3つが画面の中央にまとまっている
③ 1つ目が左端、3つ目が右端に張り付き、2つ目が中央にある（ヘッダーでよく使う形）

ヒント: 変えるのは justify-content の値だけです。flex-start / center / space-between を入れ替えて、それぞれ何が起きるか見てください。

できたら: flex-direction: column; を足すと ①〜③ の意味がどう変わりますか。justify-content が「並べている方向」の揃えだと分かれば正解です。

Grid — 格子状に並べる

Flexboxは一列に並べるのが得意ですが、縦横の格子を作るならGridが適しています。オセロの盤面（8×8）にはこちらが最適です。

.board {
  display: grid;
  grid-template-columns: repeat(8, 50px);  /* 50px幅の列を8つ */
  gap: 2px;
  background: #333;        /* 隙間が線に見える */
}
.cell {
  background: #2d7a4f;     /* マスの緑 */
  aspect-ratio: 1;         /* 正方形にする */
}

これだけで8×8の盤面ができます。repeat(8, 50px) は「50pxの列を8個」という意味です。前章の発展課題で盤面を作った人は、ここで見た目が付きます。

スマホでも崩れないようにする

画面幅に応じてスタイルを変えられます。これをレスポンシブ対応と言います。

/* 通常（PC向け） */
.row { display: flex; }

/* 画面幅が600px以下のとき */
@media (max-width: 600px) {
  .row { flex-direction: column; }  /* 縦積みに変える */
}
💡 確認方法: 開発者ツールを開き、左上のスマホアイコン（Toggle device toolbar）を押すと、スマホ表示を再現できます。実機がなくても確認できます。

ページに動きをつける

🎯 この章のゴール: 変数・条件分岐・繰り返し・関数・配列を使えるようになり、クリックに反応して画面が変わるものを作れるようになる。ここまでできればオセロが作れます。

JavaScriptとは何か

JavaScriptは、ページに動き（ロジック）を与えるプログラミング言語です。「ボタンを押したら表示を変える」「入力内容をチェックする」など、ユーザーの操作に反応する部分を担当します。

まず動かしてみる

2次元配列 — 盤面の表現

オセロの盤面のような格子は、配列の中に配列を入れることで表現します。ここは最初混乱するところなので、丁寧に見ます。

// 3×3の盤面
const board = [
  ["", "", ""],     // 0行目
  ["", "黒", ""],   // 1行目
  ["", "", "白"],   // 2行目
];

console.log(board[1][1]);   // "黒"  → board[行][列]
console.log(board[2][2]);   // "白"

board[0][0] = "黒";         // 左上に黒を置く
⚠️ [行][列] の順番: board[1][2] は「1行目の2列目」です。縦が先、横が後。ここを逆に覚えると盤面が転置してしまい、原因の分からないバグになります。紙に書いて確かめておくと確実です。
// 8×8の空の盤面を作る
const board = [];
for (let row = 0; row < 8; row++) {
  board.push(["", "", "", "", "", "", "", ""]);
}

// 全マスを調べる（二重ループ）
for (let row = 0; row < 8; row++) {
  for (let col = 0; col < 8; col++) {
    if (board[row][col] === "黒") {
      console.log(row + "行" + col + "列に黒があります");
    }
  }
}

DOM操作 — HTMLをJavaScriptから触る

ここからがWebらしい部分です。JavaScriptからHTMLの要素を取ってきて、中身を変えたり見た目を変えたりできます。この仕組みをDOMと呼びます。

// 要素を取ってくる（CSSと同じセレクタが使える）
const title = document.querySelector("#title");   // idで
const cards = document.querySelectorAll(".card"); // 複数まとめて

// 中身を変える
title.textContent = "新しいタイトル";

// CSSクラスを付け外しする
title.classList.add("active");
title.classList.remove("active");
title.classList.toggle("active");   // 有れば消す、無ければ付ける
📌 見た目の変更はクラスで: JavaScriptから直接 style.color = "red" と書くこともできますが、CSSにクラスを定義しておいて付け外しするほうが良いです。見た目の定義がCSSに集まるので、後から変更しやすくなります。第2章で「構造と見た目を分ける」と言ったのと同じ理由です。

要素を作って追加する

オセロの盤面のように、同じものを大量に並べる場合はHTMLに手で書かずJavaScriptで生成します。

const boardEl = document.querySelector("#board");

for (let row = 0; row < 8; row++) {
  for (let col = 0; col < 8; col++) {
    const cell = document.createElement("div");  // div を作る
    cell.classList.add("cell");                  // クラスを付ける
    cell.dataset.row = row;                      // 位置を覚えさせる
    cell.dataset.col = col;
    boardEl.appendChild(cell);                   // 画面に追加
  }
}

これで64個のマスが生成されます。dataset は要素に自作の情報を持たせる仕組みで、「このマスは何行何列か」を覚えさせておくとクリック時に使えます。

イベント — 操作に反応する

const btn = document.querySelector("#myButton");

btn.addEventListener("click", () => {
  console.log("押された！");
});

addEventListener は「どの要素で」「何が起きたとき」「何をするか」を登録します。clickのほか、input（入力）、submit（送信）、keydown（キー押下）などがあります。

// マスをクリックしたら、何行何列か分かる
cell.addEventListener("click", () => {
  const row = Number(cell.dataset.row);
  const col = Number(cell.dataset.col);
  console.log(row + "行" + col + "列がクリックされた");
});

エラーとの付き合い方

⚠️ ここがこの章の本題: JavaScriptからは必ずエラーに出会います。むしろエラーが出ない日はありません。大事なのは文法を覚えることではなく、エラーが出たときに自力で直せることです。

エラーが出たら、次の順番で対処します。この流れを体に入れてください。

  1. エラー文を読む — コンソール（F12）に赤い文字で出ている
  2. どこで起きたか見る — エラー文の右端にファイル名と行番号がある
  3. 原因の仮説を立てる — 「この変数が空なのでは？」など
  4. console.log で確かめる — 仮説どおりか実際に見る
  5. 修正する — 原因が分かれば直し方も分かる

履歴を残し、2人でオセロを作る

🎯 この章のゴール: 5つの基本コマンドでコードをGitHubに置けるようになり、2人で1つのリポジトリを共有してオセロを完成させる。技術より「進め方」を身につけるのが本当の目的。

なぜ今Gitを学ぶのか

Gitはコードの変更履歴を記録する道具です。TypeScriptやReactより先に学ぶのは、実際の開発では早い段階からGitを使う習慣をつけたほうが自然だからです。ここから先の演習はすべてGitで履歴を残しながら進めます。

そしてもうひとつ。ここから2人での共同作業が始まります。2人が同じファイルを別々に編集して、それを1つにまとめる——これはGitなしにはほぼ不可能です。

Gitが無い世界を想像してみる

Gitを使わずにファイルを管理すると、こうなります。見覚えがあるかもしれません。

othello.html
othello_修正.html
othello_修正2.html
othello_最終.html
othello_最終_ほんとの最終.html
othello_最終_田中さん修正版.html      ← どれが最新？

この方式には致命的な問題が3つあります。どれが最新か分からない、何をどう変えたか分からない、2人分の変更を1つにまとめられない。Gitはこの3つをすべて解決します。

知りたいことGitがあると
いまの最新はどれか常に1つのファイルだけ。最新はいつもそれ
昨日から何が変わったか変更点だけを色付きで表示できる
なぜこう直したかcommitメッセージに理由が残っている
壊す前に戻したい過去のどの時点にも戻せる
2人の変更をまとめたい自動で合成してくれる。無理な箇所だけ人間が判断する

準備 — Gitを入れて名前を設定する

第1章と同じく、ここも一度やれば以降ずっと使う設定です。まず Git for Windows（Macなら公式サイトの案内）で検索してインストールしてください。選択肢はすべて既定のままで構いません。

入ったら、VS Codeのターミナル（表示 → ターミナル）で次を実行します。これは履歴に残る「誰がやったか」の名前なので、最初に必ず設定します。

git --version                                  # 入ったか確認
git config --global user.name "Tanaka Taro"    # 履歴に残る名前
git config --global user.email "you@example.com"  # GitHubと同じアドレス
git config --global init.defaultBranch main    # 既定のブランチ名を main に
⚠️ メールアドレスはGitHubと揃える: ここで設定したアドレスがGitHubのアカウントと違うと、GitHub上で「誰のcommitか」が紐付きません。見た目の問題だけですが、2人分の作業量を確認するときに困るので最初に揃えておいてください。

次にGitHubのアカウントを作ります。無料です。作ったら、右上のアイコンから「Your repositories」→「New」で空のリポジトリを1つ作ってみてください。

💡 初回のpushで認証を求められる: 最初にpushするとき、ユーザー名とパスワードを聞かれます。ここでGitHubのログインパスワードは使えません（数年前に廃止されました）。GitHubの Settings → Developer settings → Personal access tokens でトークンを発行し、それをパスワードの代わりに貼り付けます。ここは詰まりやすいので、講師と一緒にやると早いです。

まず覚える5コマンド

git clone <URL>     # リモートのリポジトリを手元に複製する
git add .           # 変更をステージに載せる（コミット対象にする）
git commit -m "メッセージ"   # 変更を履歴として記録する
git push            # 手元の履歴をGitHubに送る
git pull            # GitHubの最新を手元に取り込む

日々の流れは「書く → add → commit → push」の繰り返しです。この5つだけで十分。branchやrebaseは後回しで構いません（チーム開発に入る段階で学びます）。

add と commit はなぜ2段階なのか

「保存するだけなのに、なぜ2回もコマンドを打つのか」——最初に必ず出る疑問です。Gitにはファイルの居場所が3つあり、addとcommitはその間を移動させる操作だからです。

[作業ディレクトリ]      [ステージ]           [リポジトリ]
いま編集中のファイル  →  次のcommitに      →  履歴として確定
              git add    載せるものを選ぶ    git commit

例: 3ファイル直したが、そのうち2つだけ記録したい
  git add index.html style.css   ← この2つだけステージに載せる
  git commit -m "盤面の見た目を整える"

つまりステージは「今回の記録に含めるものを選ぶ場所」です。慣れるまでは git add .（全部載せる）で構いません。ただ「この変更はまだ途中だから含めたくない」というときに、この2段階が効いてきます。

実は最初に覚えるべきは status と log

5コマンドより先に使うのがこの2つです。いま何が起きているかを確認するコマンドで、迷ったら必ずこれを打ちます。

git status     # いま何が変更されている？何がステージに載っている？
git log        # これまでの履歴（q キーで抜ける）
git log --oneline   # 1行ずつ簡潔に
git diff       # 前回のcommitから何が変わったか
💡 困ったら git status: Gitで詰まったときの9割は git status が答えを持っています。しかも親切に「次に打つべきコマンド」まで書いてくれます。エラーが出たら、まず status。これを習慣にしてください。

何を履歴に含めないか — .gitignore

リポジトリには入れてはいけないものがあります。パスワードなどの秘密情報、自動生成されるファイル、巨大なファイルです。これらは .gitignore というファイルに書いて除外します。

# .gitignore  ← この名前でリポジトリの一番上に置く

node_modules/     # 自動で作られる。巨大なので入れない
venv/             # Pythonの仮想環境（第5章）
.env              # APIキーやパスワード。絶対に入れない
*.db              # データベースファイル（第8章）
.DS_Store         # Macが勝手に作るファイル
⚠️ 一度pushした秘密情報は消せないと思うこと: パスワードやAPIキーをcommitしてpushすると、あとからファイルを消しても履歴には残り続けます。公開リポジトリなら世界中から見える状態です。この場合の正しい対応は「ファイルを消す」ではなく「そのキーを無効化して作り直す」です。だから最初から .gitignore に入れておくことが重要になります。

commitメッセージの書き方

メッセージは未来の自分と相方へのメモです。「何をしたか」を短く書きます。凝る必要はありませんが、次のような書き方は避けてください。

良くない例良い例なぜ
修正石が置けないバグを修正何を修正したか分からない
あああ盤面の8×8表示を追加検索しても見つけられない
いろいろ変えた手番の切り替えを実装1コミットに詰め込みすぎている合図
WIP裏返し判定の途中（縦横のみ対応）途中なら何がどこまでか書く
💡 commitの粒度: 「1日の終わりにまとめて1回」ではなく、キリのいい単位でこまめにcommitします。目安は「メッセージが1文で書ける範囲」。2つ以上のことを書きたくなったら、それは2回に分けるべきcommitです。

✏️ 練習

まず1人で慣れます。GitHubにリポジトリを作り、前章までのプロフィールカード（HTML・CSS・JSの3ファイル）をpushしてみましょう。3回以上commitを分けて、GitHub上で履歴が見えることを確認します。そのあと git log --oneline で、自分が書いたメッセージが読めるものになっているか眺めてみてください。

ここからが本番 — 2人で1つのものを作る

ここまでは1人で作ってきました。ここからは2人で1つのリポジトリを共有してオセロを作ります。これがこのコース最大の山場であり、いちばん面白いところです。

📌 なぜオセロなのか: オセロはHTML・CSS・JavaScriptだけで完成させられます。新しい技術を覚える必要がなく、ここまでの知識だけで「ちゃんと遊べるもの」が作れる。だから技術ではなく進め方に集中できます。

いきなり書き始めない — まず機能に分解する

「オセロを作ろう」と言われても、どこから手をつけるか分かりません。実務でも同じで、まず何が必要かを洗い出して、小さな単位に割るところから始めます。これを機能分解と呼びます。

2人で話し合って、オセロに必要な機能を挙げてください。以下は例です。この表を鵜呑みにせず、自分たちで考えることが課題の本体です。

機能やること難しさ
盤面を表示する8×8のマス目をHTML/CSSで作る易
石を置くクリックしたマスに石を表示する易
手番を管理する黒→白→黒…と交互に切り替える易
裏返す判定8方向を調べ、挟んだ石を裏返す難
置ける場所の判定裏返せる場所にしか置けないようにする難

💡 分解のコツ: 「1つの機能 = 半日〜1日で終わる大きさ」を目安にします。大きすぎると進捗が見えず、小さすぎると管理が面倒になります。難しさも一緒に見積もっておくと、後の分担が楽になります。

分担と順番を決める

機能が並んだら、どれから作るかと誰がやるかを決めます。順番のコツは「まず動く最小限を作る」こと。裏返し判定のような難所から始めると、何も動かない期間が長くなって心が折れます。

  1. 第1週: 盤面表示 + 石を置く（クリックしたら石が出る。ルールは無視）
  2. 第2週: 手番の切り替え + 石数表示（交互に置けるようになる）
  3. 第3週: 裏返し判定（ここが山。8方向のロジック）
  4. 第4週: 置ける場所の制限 + パス + 勝敗判定（ゲームとして完成）
📌 「動くもの」を絶やさない: この順番には理由があります。毎週の終わりに必ず何かが動いている状態を保つためです。動くものがあると、次に何をすべきかが自然に見えます。逆に「全部作り終わるまで何も動かない」進め方は、詰まったときにどこが悪いのか切り分けられず、必ず行き詰まります。

2人で回すときの約束ごと

共同作業では、作業を始める前に必ず git pull します。相方が先に何かをpushしているかもしれないからです。これを飛ばすと衝突が増えます。

# 作業を始めるとき
git pull                       # まず最新を取り込む
# …コードを書く…
git add .
git commit -m "石数の表示を追加"
git pull                       # pushの前にもう一度（相方が進んでいるかも）
git push
  • 始める前に pull、終わったら push — これを毎回やる
  • 作業を手元に溜め込まない — 3日分まとめてpushすると衝突が大きくなる
  • 担当ファイルをなるべく分ける — 同じ行を触らなければ衝突しない
  • 動かない状態でpushしない — 相方がpullした瞬間に壊れる

コンフリクト — 起きて当たり前のもの

2人が同時に同じ行を変更してpushすると、Gitが「どちらを採用すべきか分からない」と止まります。これがコンフリクトです。事故ではなく正常な動作で、共同開発をしていれば必ず起きます。

起きると、ファイルの中がこうなります。慌てず、落ち着いて読んでください。

<<<<<<< HEAD
const CELL_SIZE = 60;        ← 自分が書いた内容
=======
const CELL_SIZE = 50;        ← 相方が書いた内容
>>>>>>> main

直し方: 2人でどちらを残すか決めて、
       記号3行（<<<<<<<, =======, >>>>>>>）ごと消して
       残したい形に書き直す。両方を活かす形でもよい。
# 直したあと
git add .
git commit -m "コンフリクトを解決"
git push
⚠️ 記号を消し忘れるとコードが壊れます: <<<<<<< や ======= はGitが入れた目印であって、コードではありません。消し忘れたままcommitすると確実に動かなくなります。解決したら必ずブラウザで動作を確認してからpushしてください。

進捗を見える形にする

GitHubには Issues（課題の一覧）という機能があります。分解した機能を1つずつIssueとして登録すると、「今どれをやっているか」「どこまで終わったか」が2人で共有できます。終わったらIssueを閉じる。これだけで進捗管理になります。

リモートで離れて作業していると、相手が何をしているか見えません。Issueはその見えなさを埋めるための道具です。凝った使い方は要りません。「立てる・担当を書く・終わったら閉じる」の3つだけで十分機能します。

🛠 課題: オセロを2人で作る

共同リポジトリでオセロを完成させます。技術的な目的はGitの共同作業に慣れることですが、本当のゴールは「大きなものを小さく割って、順番に片付ける」進め方を体で覚えることです。

作るもの

  1. 2人で1つのGitHubリポジトリを作り、両方がpushできるようにする（Collaborator に追加）
  2. .gitignore を最初に置いておく
  3. 2人で話し合ってオセロの機能を洗い出し、Issueとして登録する
  4. どれから作るか順番を決め、担当を分ける
  5. 週ごとに区切って進める。毎回こまめにcommit・pushする
  6. 作業を始める前に必ず pull する習慣をつける
  7. 相手のコードを読み、気付いたことを伝え合う
  8. 完成したら2人で対戦してみる

2人とも遊べるオセロが動いている

💡 完璧を目指さないこと。まず「石が置けるだけ」の状態でいいので動かす。動くものがあると、次に何をすべきかが自然に見えてきます。逆に、全部作り終わるまで動かないやり方は必ず行き詰まります。

💡 詰まったときの合図: 裏返し判定は多くの人が詰まります。8方向をどう表現するか、で悩んだら「方向を [x, y] の組で配列に持つ」と考えてみてください。それ以上は自分たちで調べてみましょう。

決定的な違い — インデントがブロックを決める

JavaScriptは波括弧 { } で処理のまとまりを表しますが、Pythonは行頭の空白（インデント）でそれを表します。波括弧もセミコロンもありません。

def check(n):
    if n > 0:
        print("正の数")
        print("この2行はif の中")
    print("この行はif の外（関数の中）")
print("この行は関数の外")
⚠️ 最初はここで必ず詰まる: インデントがずれると IndentationError というエラーになります。エラーが出たらまず行頭の空白を疑ってください。スペース4つで揃えるのが慣習です。エディタの設定でタブとスペースが混ざると厄介なので、VS Codeの設定を確認しておきましょう。
💡 VS Code の設定を1つだけ: 画面右下に「スペース: 4」と出ているか確認してください。「タブのサイズ」表示になっていたらクリックして「スペースによるインデント」に変えます。タブとスペースが混ざったファイルは、見た目が同じでもPythonがエラーを出します。原因が目に見えないので、最初に設定しておくのが安全です。

繰り返しの書き方

オセロの盤面は8×8のマスなので、繰り返しを多用します。JSの for (let i = 0; i < 8; i++) にあたるのが range() です。

for i in range(8):        # 0, 1, 2, ... 7（8は含まない）
    print(i)

for i in range(1, 9):     # 1 から 8 まで
    print(i)

# 中身を直接まわす（JSの for...of）
for f in ["りんご", "みかん"]:
    print(f)

# 番号と中身の両方が欲しいとき
for i, f in enumerate(["りんご", "みかん"]):
    print(i, f)           # 0 りんご / 1 みかん

# 条件が続く間くり返す
count = 0
while count < 3:
    count = count + 1
📌 range(8) が 0〜7 なのはJSと同じ考え方: 第3章で「0から数える」を学びました。Pythonも同じです。range(8) は「8個ぶん、0から数える」 という意味なので、8は含まれません。8×8の盤面を全部まわすなら for row in range(8): for col in range(8): の二重ループになります。

2次元リスト — オセロの盤面

第3章でJavaScriptの2次元配列を扱いました。Pythonでもまったく同じ考え方で書けます。board[行][列] です。

# 8×8を空（0）で初期化する
board = [[0] * 8 for _ in range(8)]

# 中央4マスに初期配置（1=黒, 2=白）
board[3][3] = 2
board[3][4] = 1
board[4][3] = 1
board[4][4] = 2

# 盤面を文字で表示する
MARK = {0: ".", 1: "●", 2: "○"}
for row in board:
    print(" ".join(MARK[cell] for cell in row))
⚠️ 盤面の作り方でよくある罠: board = [[0] * 8] * 8 と書きたくなりますが、これは動きません。
同じ行が8個並んでいるだけなので、1マス変えると8行すべてが変わります。

正しくは [[0] * 8 for _ in range(8)] のように、行を8回作ります。
これはPython特有の落とし穴で、多くの人が一度は踏みます。

データの置き場所を設計する

🎯 この章のゴール: オセロの戦績を保存するテーブルを自分で設計できるようになる。あわせてSQLの基本操作を覚え、データの出し入れができるようにする。

なぜデータベースが要るのか

前章でPythonを覚えましたが、プログラムの中の変数は実行が終われば消えます。オセロの対戦結果を後から見返したいなら、どこかに書き残さないといけません。その置き場所がデータベース（DB）です。

「ファイルに書けばいいのでは」と思うかもしれません。実際できます。ただ、探す・並べ替える・複数人が同時に書くといったことをファイルでやると大変です。DBはそれを得意とする専用の道具です。

やりたいことファイルでやるとDBなら
直近5件だけ見たい全部読んで並べ替えて切り出すORDER BY ... LIMIT 5 の1行
黒の勝ち数を数えたい全行を読んで自分で数えるCOUNT で一発
2人が同時に書き込む片方の書き込みが消える事故が起きるDBが順番を管理してくれる
数値の列に文字が入る気付かず壊れたまま進む型が合わないと拒否してくれる

どのDBを使うか

DBにはいくつも製品があります。書き方（SQL）はほぼ共通なので、まずは一番手軽なSQLiteで始めて、必要になったら移ります。

製品特徴このコースでは
SQLiteファイル1つで動く。インストール不要まずこれ。学習に最適
PostgreSQL本格的。実務で広く使われる余裕があれば / デプロイ時に
MySQL同じく定番。Webサービスで多い触れなくてよい
💡 SQLiteの見方: SQLiteは othello.db のようなただのファイルです。中身を見るには「DB Browser for SQLite」という無料ソフトを入れるのが手軽です。VS Codeの拡張機能（SQLite Viewer など）でも見られます。表として目で見られる状態にしておくと、SQLの結果が腹落ちします。

テーブル = 表

DBの中では、データをテーブルという表の形で持ちます。Excelのシートを思い浮かべてください。列（どんな項目か）と行（1件ずつのデータ）でできています。

📌 設計でいちばん大事な問い: 「この表の1行は、何を表しているのか」 を一言で言えるようにすること。上の表なら「1行 = 1回の対戦」です。これが曖昧なまま作ると、後で必ず破綻します。

設計は「作りたい画面」から逆算する

いきなり列を並べようとすると手が止まります。先に「どんな画面を作りたいか」を言葉にして、そこから必要な項目を引き出すと進みます。

作りたい画面そのために必要な情報
直近の対戦一覧勝者・石数・対戦日時
勝率ランキング誰が対戦したか（プレイヤー）・勝敗
1試合の詳細上のすべて + 手数など
月別の対戦数対戦日時（日付として扱える形で）
💡 日時は必ず入れておく: 迷ったら「いつ」を表す列は入れておくのが鉄則です。後から「新しい順に並べたい」「今月だけ見たい」と必ず言われます。逆に、後から過去のデータに日時を足すことはできません（そのデータがいつのものか、もう分からないため）。

列には型を決める

各列には「どんな種類のデータが入るか」（型）を決めます。数値の列に文字を入れようとするとDBが拒否してくれるので、おかしなデータが混ざるのを防げます。

CREATE TABLE games (
  id           INTEGER PRIMARY KEY,   -- 主キー。行を特定する
  winner       TEXT NOT NULL,         -- 文字。空は許さない
  black_count  INTEGER NOT NULL,      -- 整数
  white_count  INTEGER NOT NULL,
  played_at    TIMESTAMP DEFAULT NOW() -- 日時。既定は今
);
  • INTEGER … 整数
  • TEXT … 文字列
  • BOOLEAN … true / false
  • TIMESTAMP … 日時
  • PRIMARY KEY … その行を特定する列。重複できない
  • NOT NULL … 空を許さない

主キーにはその行だけを指せる値を入れます。ふつうは連番の id で構いません。「プレイヤー名を主キーにする」のは避けてください。同姓同名が来た瞬間に破綻しますし、改名もできなくなります。

4つの基本操作（CRUD）

-- Create: 追加する
INSERT INTO games (winner, black_count, white_count)
VALUES ('黒', 38, 26);

-- Read: 取り出す
SELECT * FROM games;                          -- 全部
SELECT winner, played_at FROM games;          -- 列を選ぶ
SELECT * FROM games WHERE winner = '黒';      -- 条件つき
SELECT * FROM games ORDER BY played_at DESC;  -- 新しい順
SELECT * FROM games ORDER BY played_at DESC LIMIT 5;  -- 直近5件

-- Update: 書き換える
UPDATE games SET winner = '白' WHERE id = 1;

-- Delete: 消す
DELETE FROM games WHERE id = 1;
⚠️ WHERE を忘れると全部消える: DELETE FROM games; と書くと全行が消えます。UPDATE も同じで、WHERE無しだと全行が書き換わります。実務でもっとも怖い事故のひとつです。DELETE や UPDATE を書くときは、先に同じ条件で SELECT して対象を確認する癖をつけてください。

条件の書き方

WHERE には条件を組み合わせて書けます。JavaScriptの if に近い感覚です。

WHERE winner = '黒' AND black_count > 40      -- かつ
WHERE winner = '黒' OR winner = '白'          -- または
WHERE winner IN ('黒', '白')                  -- 上と同じ意味。こちらが簡潔
WHERE black_count BETWEEN 30 AND 40           -- 範囲
WHERE winner LIKE '黒%'                       -- 「黒」で始まる
WHERE played_at >= '2026-08-01'               -- 日付で絞る
WHERE memo IS NULL                            -- 値が入っていない行
⚠️ NULL は = NULL では取れません: 「値が入っていない」状態を NULL と呼びます。NULL は「不明」を意味するので、= NULL は真にも偽にもなりません。IS NULL / IS NOT NULL を使ってください。ここは初心者が必ず一度は引っかかる箇所です。

数える・集計する

ランキングを作るには集計が要ります。「全部取ってきてPythonで数える」より、SQLで数えたほうが圧倒的に速く、コードも短くなります。

SELECT COUNT(*) FROM games;                     -- 全対戦数
SELECT COUNT(*) FROM games WHERE winner = '黒'; -- 黒の勝ち数
SELECT AVG(black_count) FROM games;             -- 黒の平均石数
SELECT MAX(black_count) FROM games;             -- 最大

-- 勝者ごとに数える（GROUP BY）
SELECT winner, COUNT(*) AS wins
FROM games
GROUP BY winner
ORDER BY wins DESC;
📌 GROUP BY は「同じ値ごとに束ねる」: 上のSQLは「winnerが同じ行をまとめて、それぞれ何行あるか数える」という意味です。結果は「黒: 12勝 / 白: 9勝 / 引き分け: 2」のような形になります。ランキング画面はほぼこれで作れます。

表を分ける — 外部キー

「誰が対戦したか」も残したくなったとします。プレイヤー名を games テーブルに直接書くこともできますが、名前が変わったとき全行を直すことになります。そこで表を分けて、繋ぐという考え方を使います。

CREATE TABLE players (
  id    INTEGER PRIMARY KEY,
  name  TEXT NOT NULL
);

CREATE TABLE games (
  id            INTEGER PRIMARY KEY,
  black_player  INTEGER REFERENCES players(id),  -- 外部キー
  white_player  INTEGER REFERENCES players(id),
  winner        TEXT NOT NULL,
  black_count   INTEGER NOT NULL,
  white_count   INTEGER NOT NULL,
  played_at     TIMESTAMP DEFAULT NOW()
);

games には名前ではなくプレイヤーのidを持たせます。こうすると名前を変えたいとき players を1行直すだけで済みます。

📌 原則は「同じ情報を2箇所に書かない」: 表を分ける理由はこれに尽きます。同じ情報が2箇所にあると、片方だけ直されて食い違うという事故が必ず起きます。「この情報の正しい置き場所はどこか」を1つに決める——これが設計の基本です。

繋いで取り出す — JOIN

表を分けると、取り出すときに繋ぎ直す必要があります。それが JOIN です。

SELECT
  g.id,
  b.name AS black_name,
  w.name AS white_name,
  g.winner,
  g.played_at
FROM games g
JOIN players b ON g.black_player = b.id
JOIN players w ON g.white_player = w.id
ORDER BY g.played_at DESC;

FROM games g の g は別名です。長いテーブル名を毎回書かずに済み、同じ表を2回繋ぐとき（上の例では players を黒用・白用の2回）に区別できます。ON の部分が「どの列とどの列が同じ行を繋ぐか」の指定です。

💡 まずは分けずに作ってもいい: 最初から完璧な設計を目指すと進みません。1つのテーブルで作ってみて、不便を感じてから分けるほうが、なぜ分けるのかが腹落ちします。実際の開発でも設計は途中で変わります。

🔌 API

ブラウザとサーバをつなぐ

🎯 この章のゴール: FastAPIでサーバを立て、オセロの画面から戦績を送って一覧を取得できるようにする。ブラウザとサーバが別プログラムとして動いていることを、目で見て確認する。

いま2つのプログラムがある

ここまでで、ブラウザで動くオセロ（HTML/CSS/JS）と、Pythonで書いたコード、そしてデータベースができました。これらはそれぞれ別の場所で動く、別のプログラムです。

[ブラウザ]              [サーバ]
HTML/CSS/JS      ？      Python + DB
オセロの画面     ←→      戦績の保存先

この「？」の部分をつなぐのが API

ブラウザのJavaScriptから、サーバのPythonの関数を直接呼ぶことはできません。間にHTTPという約束事を挟んで、JSONという形式でデータをやり取りします。その窓口がAPIです。

なぜブラウザから直接DBに繋がないのか

素朴な疑問として「JavaScriptから直接データベースを触れば早いのでは」と思うはずです。技術的にできなくはないが、絶対にやってはいけない——理由は3つあります。

  • 接続情報が丸見えになる … ブラウザに送ったコードは誰でも読めます。DBのパスワードを書けば、全世界に公開したのと同じです
  • 何でもできてしまう … DBに直接繋げるなら、DELETE FROM games を打たれても止められません
  • ルールを置く場所が無くなる … 「石数は0〜64の範囲」のような検証を、信用できない場所（ブラウザ）でしか行えなくなります
📌 APIは「受付」である: APIは、DBの前に立つ受付だと考えてください。ブラウザからのお願いを受け取り、内容を検査し、問題なければDBに取り次ぐ。この関所があるから、ブラウザ側が何をしようとサーバのルールを守らせられます。「ブラウザから来るデータは信用しない」——これはWeb開発の大原則です。

HTTP — やり取りの約束事

ブラウザとサーバの会話は、必ず「リクエストを送って、レスポンスが返る」の1往復です。1回のやり取りで完結し、サーバは前回のことを覚えていません。

[リクエスト] ブラウザ → サーバ
  メソッド:  POST                      ← 何をしたいか
  URL:      /api/games                ← どこに対して
  ヘッダ:    Content-Type: application/json   ← 補足情報
  ボディ:    {"winner": "黒", ...}     ← 送るデータ

[レスポンス] サーバ → ブラウザ
  ステータス: 200 OK                   ← 結果
  ボディ:    {"ok": true}              ← 返すデータ

窓口の作り方 — URLとメソッド

APIは「どのURLに」「どの方法で」アクセスするかで機能が決まります。この組み合わせ1つ1つをエンドポイントと呼びます。

メソッドURLやること
GET/api/games戦績の一覧を取得する
POST/api/games対戦結果を1件追加する
GET/api/games/33番の対戦の詳細を取得する
DELETE/api/games/33番の対戦を削除する
💡 前章とのつながり: この4つは、SQLで学んだ CRUD（INSERT / SELECT / UPDATE / DELETE）ときれいに対応します。APIは「外から使えるようにしたCRUD」だと考えると分かりやすくなります。

URLに同じ /api/games が2回出てくることに注目してください。URLは「何を扱うか（戦績というデータ）」を表し、メソッドが「それをどうするか」を表します。この分け方が身につくと、API設計で迷わなくなります。

ステータスコード — 結果は番号で返る

レスポンスには必ず3桁の番号が付きます。最初の1桁を見れば、誰のせいかが分かります。

番号意味誰の問題か
200 OK成功—
201 Created作成に成功—
400 Bad Request送ったリクエストがおかしいブラウザ側
404 Not FoundそのURLは無いブラウザ側（URLの打ち間違い）
422 Unprocessableデータの形が期待と違うブラウザ側（送る中身）
500 Internal Server Errorサーバの中でエラーが起きたサーバ側
📌 4xx と 5xx の切り分けが最重要: 400番台は「送った側が悪い」、500番台は「受けた側が悪い」。これだけ覚えておけば、詰まったときにどちらのコードを見るべきかが即座に決まります。想像で直し始める前に、まず番号を見てください。

JSON — 共通のデータ形式

PythonとJavaScriptは別の言語なので、そのままではデータを渡せません。そこで両方が読み書きできるテキスト形式に変換します。それがJSONです。

// JSONの実体はただの文字列
{"winner": "黒", "black_count": 38, "white_count": 26}

// JavaScript側
JSON.stringify(obj)   // オブジェクト → JSON文字列（送るとき）
JSON.parse(text)      // JSON文字列 → オブジェクト（受けるとき）

# Python側は FastAPI が自動で変換してくれる
# 辞書を return するだけでJSONになる

形はJavaScriptのオブジェクト、Pythonの辞書とほぼ同じです。キーは必ずダブルクォートで囲む、末尾にカンマを付けられない、といった細かい制約があります。

FastAPIでサーバを書く

PythonでAPIを作るライブラリはいくつかありますが、ここでは FastAPI を使います。書く量が少なく、自動でAPIの説明ページを作ってくれるのが大きな利点です。

pip install fastapi uvicorn
# main.py
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

# 受け取るデータの形を決めておく
class Game(BaseModel):
    winner: str
    black_count: int
    white_count: int

games = []   # ひとまずメモリに置く（次章でDBに移す）

@app.get("/api/games")
def list_games():
    return games

@app.post("/api/games")
def add_game(game: Game):
    games.append(game)
    return {"ok": True, "count": len(games)}

@app.get("/api/games") の部分が「このURLにGETが来たら、下の関数を動かす」という指定です。関数が返した辞書やリストは、FastAPIが自動でJSONに変換して返してくれます。

📌 class Game が検査をしている: BaseModel を継承したクラスは、受け取るデータの形の宣言です。black_count: int と書いておけば、文字列が送られてきた時点でFastAPIが自動で弾き、422を返します。さきほどの「ブラウザから来るデータは信用しない」を、書くだけで実現してくれる仕組みです。
uvicorn main:app --reload      # サーバを起動する
# → http://127.0.0.1:8000 で動く
# 止めるときは Ctrl + C

127.0.0.1 は「自分のPC」を指す特別なアドレスで、localhost と書いても同じです。:8000 はポート番号——1台のPCの中で複数のサーバを区別するための番号です。すでに使われていると Address already in use と出るので、その場合は別の番号にします。

📌 まずは /docs を開くこと: サーバを起動したら http://127.0.0.1:8000/docs を開いてください。FastAPIが自動で作ったAPIの操作画面が出ます。ここから実際にデータを送って試せるので、ブラウザ側を書く前にサーバだけで動作確認できます。切り分けができるので、詰まったときの強い味方になります。

ブラウザ側から呼ぶ

サーバが動いたら、オセロの画面から呼びます。JavaScriptの fetch を使います。

// 対戦が終わったら結果を送る
async function saveResult(winner, black, white) {
  const res = await fetch("http://127.0.0.1:8000/api/games", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      winner: winner,
      black_count: black,
      white_count: white,
    }),
  });
  const data = await res.json();
  console.log("保存しました", data);
}

// 戦績一覧を取ってくる
async function loadHistory() {
  const res = await fetch("http://127.0.0.1:8000/api/games");
  const games = await res.json();
  return games;
}

async と await — 返事を待つということ

見慣れない async と await が出てきました。通信は時間がかかる——ここまでの処理と決定的に違う点です。

サーバへのリクエストは、返事が来るまで数十ミリ秒〜数秒かかります。その間ブラウザが固まっては困るので、JavaScriptは「返事は後で来るので、先に進んでおく」という動き方をします。await は「ここは返事を待ってから次に進む」という指示です。

// ❌ awaitを付け忘れると
const res = fetch(url);
console.log(res);        // → Promise { <pending> } と出る（まだ返事が来ていない）

// ⭕ await を付ける
const res = await fetch(url);
const data = await res.json();   // json() も時間がかかるので await が要る
console.log(data);       // → 中身が出る
⚠️ await は async の中でしか書けません: await を使う関数には必ず async を付けます。忘れると await is only valid in async functions というエラーになります。「Promise { pending } と表示された」ときは、ほぼ await の付け忘れです。この2つはセットだと覚えてください。

失敗したときの処理も書く

通信は失敗します。サーバが落ちている、URLが違う、ネットワークが切れている——どれも普通に起きます。fetch は404や500でもエラーにならないので、自分で確認する必要があります。

async function loadHistory() {
  try {
    const res = await fetch("http://127.0.0.1:8000/api/games");
    if (!res.ok) {                       // 404や500はここで捕まえる
      console.error("失敗:", res.status);
      return [];
    }
    return await res.json();
  } catch (e) {
    // サーバが起動していない・ネットが切れている等はこちら
    console.error("通信できませんでした", e);
    return [];
  }
}
⚠️ ここで必ず CORS エラーが出ます: ブラウザは安全のため、別の場所にあるサーバへの通信を既定で止めます。コンソールに「CORS policy」というエラーが出たら、これです。バグではなくブラウザの正しい動作なので、サーバ側で「このオリジンからは許可する」と設定します。
# main.py に追記
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],      # 学習用。本番では実際のURLを指定する
    allow_methods=["*"],
    allow_headers=["*"],
)

なぜこんな制限があるのか。もし無ければ、悪意あるサイトを開いただけで、そのJavaScriptがあなたのログイン中の銀行サイトへ勝手にリクエストを送れてしまうからです。CORSは「このサイトからのアクセスは許可する」とサーバ側が明示する仕組みで、あなたを守っている側の機能です。

Networkタブを読む

通信の問題は、開発者ツールのNetworkタブを開けば事実が見えます。想像で直そうとせず、必ずここを見てください。第1章で開いた開発者ツール（F12）の中にあります。

  1. F12 で開発者ツールを開き、Network タブを選ぶ
  2. 画面を操作してリクエストを発生させる（一覧ボタンを押す等）
  3. 一覧に行が出るか確認する。出ないならリクエスト自体が飛んでいない（JSのエラーを疑う）

🗄️ DB連携

サーバからデータを保存する

🎯 この章のゴール: 前章のAPIをDBに繋ぎ、サーバを再起動しても戦績が残る状態にする。Webアプリの3層構成を自分の言葉で説明できるようになる。

全体像がつながる

ここまでに作ったものが、いよいよ1本につながります。

[ブラウザ]          [サーバ]              [DB]
オセロの画面   →    FastAPI        →    games テーブル
HTML/CSS/JS   ←    Python         ←    players テーブル

  fetch()          エンドポイント        SQL

この3層の絵が描ければ、Webアプリの基本は理解できたと言えます。APIがブラウザとDBの橋渡しをしている——これがいちばん大事な理解です。

📌 それぞれの持ち場: ブラウザは「見せる・受け取る」だけ。APIは「検査する・判断する・取り次ぐ」。DBは「正しく保管する」。この分担がはっきりしていると、不具合が起きたときどこを見ればいいかが即座に分かります。逆に、ブラウザに判断を書き、DBに検査を任せる——のように混ざると、途端に手に負えなくなります。

PythonからDBに繋ぐ

まずは生のSQLで動かします。SQLiteなら追加のインストールも要りません（Pythonに最初から入っています）。

# db.py
import sqlite3

def get_conn():
    conn = sqlite3.connect("othello.db")
    conn.row_factory = sqlite3.Row   # 辞書のように使えるようにする
    return conn

def init_db():
    conn = get_conn()
    conn.execute("""
        CREATE TABLE IF NOT EXISTS games (
          id          INTEGER PRIMARY KEY AUTOINCREMENT,
          winner      TEXT NOT NULL,
          black_count INTEGER NOT NULL,
          white_count INTEGER NOT NULL,
          played_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        )
    """)
    conn.commit()
    conn.close()

3つ、意味を確認しておきます。

  • IF NOT EXISTS … すでにテーブルがあれば何もしない。起動のたびに呼んでも安全
  • row_factory = sqlite3.Row … 結果を row["winner"] のように名前で取り出せるようにする。これが無いと番号（row[0]）でしか取れず、列を足したとき壊れます
  • conn.close() … 使い終わった接続を閉じる。閉じないと接続が溜まり、いずれ繋がらなくなります

なぜファイルを db.py と main.py に分けるのか

全部 main.py に書いても動きます。それでも分けるのは、1つのファイルに1つの役割を持たせるためです。これを責務の分離と呼びます。

ファイル役割ここに書かないもの
db.pyDBへの接続とSQLURLの定義・HTTPの話
main.pyエンドポイントの定義SQLの文字列

分けておくと、あとで「SQLiteをPostgreSQLに変える」となったとき db.py だけ直せば済みます。混ざっていると、全ファイルからSQLを探し出すことになります。コードレビューで最初に見られるのもここです。

APIをDBに繋ぎ替える

前章では戦績をリスト（メモリ）に入れていました。そこをDBの読み書きに置き換えます。

# main.py
from db import get_conn, init_db

init_db()          # 起動時にテーブルを用意しておく

@app.get("/api/games")
def list_games():
    conn = get_conn()
    rows = conn.execute(
        "SELECT * FROM games ORDER BY played_at DESC"
    ).fetchall()
    conn.close()
    return [dict(r) for r in rows]

@app.post("/api/games")
def add_game(game: Game):
    conn = get_conn()
    conn.execute(
        "INSERT INTO games (winner, black_count, white_count) VALUES (?, ?, ?)",
        (game.winner, game.black_count, game.white_count),   # ← 値は別で渡す
    )
    conn.commit()
    conn.close()
    return {"ok": True}
⚠️ commit を忘れると保存されません: INSERT や UPDATE を実行しただけでは、まだ確定していません。conn.commit() を呼んで初めてファイルに書き込まれます。「エラーは出ないのにデータが入らない」という症状の原因は、ほぼこれです。SELECTには要りません（読むだけなので）。
📌 ここが本章のハイライト: この状態でサーバを再起動してから一覧を見てください。データが残っているはずです。前章までは消えていました。この違いが「保存する」ということです。

絶対にやってはいけない書き方

上のコードで、値を ? で書いて別に渡しているのには理由があります。もし文字列を繋げて書くと、入力次第でSQLを乗っ取られます。

# ❌ 絶対にダメな書き方
name = 受け取った値
conn.execute("SELECT * FROM players WHERE name = '" + name + "'")

# もし name に  ' OR '1'='1  が入ったら、実行されるSQLは
# SELECT * FROM players WHERE name = '' OR '1'='1'
# → 全件が返ってくる（条件が無意味になる）

# もっと悪いと  '; DROP TABLE games; --  で表ごと消される
# ⭕ 正しい書き方（プレースホルダを使う）
conn.execute("SELECT * FROM players WHERE name = ?", (name,))

なぜこれで防げるのか。プレースホルダを使うと、DBは「SQLの文」と「値」を別々に受け取ります。値の中に何が書かれていても、それはただの文字列として扱われ、命令としては解釈されません。文字列連結だと、DBには繋がった1本の文しか届かないので、区別のしようがないのです。

⚠️ SQLインジェクション: これは実際に起き続けている代表的な攻撃です。「自分のアプリは小さいから大丈夫」ということはありません。ユーザーからの入力をSQLに文字列連結しない——これだけは例外なく守ってください。f文字列（f\"... {name} ...\"）で組み立てるのも同じく危険です。
💡 一度実際に試してみる: 学習用の自分のDBで、わざと文字列連結版を書いて ' OR '1'='1 を入れてみてください。全件返ってくるのを自分の目で見ると、二度と忘れません。言葉で聞くだけでは身につかない部分です。必ず自分のPC上の練習用DBで行い、他人のシステムには絶対に試さないこと。

接続情報をコードに書かない

SQLiteはファイル名だけですが、PostgreSQLなどに移るとホスト名・ユーザー名・パスワードが必要になります。これらをコードに直接書いてはいけません。第4章で学んだとおり、pushした瞬間に公開されます。

# .env  ← .gitignore に入れる。commitしない

# db.py
import os
DB_PATH = os.environ.get("DB_PATH", "othello.db")   # 環境変数から読む

こうしておくと、手元では othello.db、公開先では本番のDB、とコードを変えずに切り替えられます。次章のデプロイでそのまま効いてきます。

ORM — SQLをコードで書く

生SQLで仕組みが分かったら、ORMという道具に進めます。SQLをPythonのコードとして書けるようになり、プレースホルダも自動で使われるので安全です。

# SQLAlchemy を使った例
games = session.query(Game).order_by(Game.played_at.desc()).all()

session.add(Game(winner="黒", black_count=38, white_count=26))
session.commit()
💡 なぜ生SQLを先にやったか: ORMは便利ですが、中で何が起きているか分からないまま使うと詰まったとき何もできません。生SQLを知っていれば「ORMがどんなSQLを出しているか」を確認して原因を追えます。順番が大事です。

「もし1万件あったら？」

いま戦績は数十件でしょう。だから SELECT * FROM games で全部取ってきても一瞬です。でも1万件になったら？ 一覧画面を開くたびに1万行を読み、JSONに変換し、ブラウザに送ることになります。

-- ❌ 全部取ってきてから、Python側で最初の20件だけ使う
SELECT * FROM games;

-- ⭕ 必要な分だけDBに取ってこさせる
SELECT * FROM games ORDER BY played_at DESC LIMIT 20;
📌 データが増えたときを想像する癖: いま動いているコードに対して「もし100倍のデータがあったら、これは動くか」と自問してみてください。この問いを習慣にできるかどうかが、動くコードを書ける人と、使われるコードを書ける人の分かれ目です。

  • 該当0件として何も返らない
答えと解説

正解: 条件が常に真になり、全件が返ってしまう

🚀 デプロイ

世界に公開する

🎯 この章のゴール: 自分の作ったWebアプリをインターネットに公開し、公開URLを人に送って遊んでもらうところまでを体験する。ここまでの全部の総仕上げです。

デプロイとは何か

デプロイとは、手元で動いているアプリをインターネット上のサーバーに配置して、誰でも使える状態にすることです。

コードを書く
   ↓
GitHubへ push
   ↓
ホスティングサービスが自動でビルド・公開
   ↓
https://あなたのアプリ.vercel.app  ← 世界中からアクセスできる

なぜ localhost では駄目なのか

前章までのオセロは http://127.0.0.1:8000 で動いていました。この住所は「自分のPC」を指しています。同じURLを友達に送っても、相手のPCの中を見に行くだけで、あなたのアプリには繋がりません。

localhostデプロイ後
見られる人自分だけ世界中の誰でも
動いている時間自分がPCを起動している間だけ24時間ずっと
URL127.0.0.1:8000https://…（本物のドメイン）
止まるときターミナルを閉じたら自分で止めるまで
📌 「誰かのPCで動き続けている」だけ: デプロイと聞くと特別なことに思えますが、やっていることは「自分のPCの代わりに、24時間動いているどこかのコンピュータでプログラムを動かす」だけです。ホスティングサービスは、そのコンピュータを貸してくれる会社です。仕組みが分かれば怖くありません。

2種類のデプロイがある

自分のアプリがどちらなのかで、選ぶサービスが変わります。オセロは両方を含んでいます。

種類中身必要なもの
静的サイトHTML / CSS / JS だけファイルを置く場所だけあればよい
サーバが要るアプリPython が動き続ける + DBプログラムを実行し続けられる環境

つまりオセロの公開は2つの場所へのデプロイになります。画面（フロント）を1か所、API + DB（バック）をもう1か所。そして両者をURLで繋ぎ直します。ここが唯一ややこしい部分です。

今どきのデプロイはGit連携

VercelやNetlify、Render などのホスティングサービスは、GitHubのリポジトリを連携するだけで、pushのたびに自動で最新版を公開してくれます。第4章で身につけたGitの習慣がここで直接活きます。

  • フロントエンド（HTML/CSS/JS）… Vercel / Netlify / GitHub Pages などが定番
  • API + DB … Render / Railway など、DBも一緒に提供するサービスが手軽

基本の流れは、どのサービスでもほぼ同じです。

  1. サービスにGitHubアカウントでログインする
  2. 「New Project」などから、公開したいリポジトリを選ぶ
  3. ビルド設定と公開するフォルダを指定する（静的サイトなら大抵そのままでよい）
  4. 環境変数を設定する（次の節）
  5. Deploy を押す。数分待つとURLが発行される
💡 pushしたら自動で反映される: 一度つなげば、あとは git push するだけで公開版が更新されます。手作業でファイルをアップロードする必要はありません。「pushしたら数分後に本番が変わる」という感覚を、ここで一度味わっておいてください。

環境変数 — 秘密をコードの外に置く

第8章で .env に接続情報を書きました。このファイルは .gitignore に入れているので、GitHubには上がっていません。ということは、公開先のサーバにも届いていません。

そこで、ホスティングサービスの管理画面から環境変数を設定します。多くのサービスに「Environment Variables」という項目があります。

手元（.env ファイル）        公開先（サービスの管理画面）
  DB_PATH=othello.db    →    DB_PATH=/data/othello.db
  API_URL=127.0.0.1:8000 →   API_URL=https://xxx.onrender.com

コードは同じまま。値だけが場所によって変わる
📌 これが第8章で環境変数にした理由: もし接続情報をコードに直接書いていたら、公開のたびにコードを書き換えることになります。「環境ごとに変わるものは、コードの外に出す」——この原則が、ここで具体的な形で効いてきます。

公開前チェック

⚠️ 公開は取り消せないと思うこと: 一度インターネットに出したものは、消しても誰かの手元に残っている可能性があります。特にリポジトリを公開（public）にする場合は、履歴のすべてが見られます。第4章で学んだとおり、過去のcommitに秘密情報が残っていれば、それも見えます。押す前に必ず確認してください。

公開前に確認すること

APIキー・パスワードがコードに書かれていない
.env が .gitignore に入っていて、commitされていない
過去のcommit履歴にも秘密情報が残っていない
CORSの許可を「なんでも許可」のままにしていない
個人情報・実在の住所や電話番号を含むテストデータが入っていない
DELETE系のAPIに、誰でも叩ける状態で危険なものが無い
リポジトリを public にしてよいか2人で確認した

「手元では動くのに本番で動かない」

デプロイして最初にほぼ必ず起きます。バグではなく、環境の違いです。原因はだいたいこの5つに絞られます。

症状原因対処

起動に失敗するライブラリが入っていないrequirements.txt を用意したか確認

しばらくするとデータが消える保存先が一時的な場所永続化されるDBを使う（下記）
⚠️ SQLiteファイルが消えることがある: サービスによっては、再起動のたびにファイルが初期状態に戻ります（アプリを動かす場所と、データを残す場所が別になっているため）。手元では消えないのに本番だけ消える、という現象の正体はこれです。対処は、そのサービスが提供する永続ディスクを使うか、PostgreSQLなどの独立したDBサービスに移すことです。第6章で「SQLは製品が変わってもほぼ同じ」と書いたのは、ここで効いてきます。

ログを読む

本番では print の出力が画面に見えません。代わりに、サービスの管理画面に「Logs」という項目があります。第7章でターミナルのエラーを読んだのと同じことを、ここで行います。

  1. 管理画面の Logs（またはDeploy Logs）を開く
  2. デプロイ時のエラーか、実行時のエラーかを見分ける
  3. Pythonのエラーが出ていれば、手元と同じように読む
  4. 直したら push する。自動で再デプロイされる
💡 切り分けは今までと同じ: 本番だからといって特別なことはありません。Networkタブでリクエストを見て、ログでサーバ側を見る。第7章で身につけた切り分けが、そのまま通用します。「本番だから分からない」と思った瞬間に手が止まるので、いつもの手順に落として考えてください。

🔷 TypeScript

型でオセロを安全にする（発展）

🎯 この章のゴール: 「型があると実行する前に間違いに気付ける」価値を体感し、基本の型注釈とinterfaceを書けるようになる。完成したオセロを型付きに書き直すのが課題です。

TypeScriptとは何か

TypeScriptは、JavaScriptに型を追加した言語です。書いたコードはJavaScriptに変換されて動きます。つまり「JavaScriptの上位互換」で、これまで学んだ文法はそのまま使えます。

型とは「この変数には何が入るか」の宣言です。数値なのか、文字列なのか、あるオブジェクトなのか。それを書いておくと、違うものを入れようとした瞬間にエディタが教えてくれます。

なぜ型が要るのか — オセロで起きたこと

抽象的な説明より、実際に起きやすいバグを見たほうが早いです。次のコードはJavaScriptでは何のエラーも出ません。

// 石を置く関数（片方が書いた）
function putStone(row, col, color) {
  board[row][col] = color;
}

// 呼ぶ側（もう片方が書いた）
putStone(3, 4, "黒");      // ある人は日本語で
putStone("3", "4", "black"); // 別の人は文字列と英語で

// 数える側
function countBlack() {
  // "black" で数えている → 日本語の "黒" は数えられない
}

2人で開発していると、こういう食い違いが必ず起きます。しかもJavaScriptは何も言わずに動くので、「なぜか石数が合わない」という形で、ずっと後になってから発覚します。原因を探すのに何時間もかかることがあります。

📌 型は「相方への約束」でもある: 型を書くということは、「この関数はこういうものを受け取ります」と明文化することです。共同開発では、相手のコードを全部読まなくても、型を見れば使い方が分かります。第4章でやった共同開発の苦労を、型が減らしてくれます。

型注釈の基本

let count: number = 0;
let name: string = '田中';
let done: boolean = false;
let tags: string[] = ['html', 'css'];

function add(a: number, b: number): number {
  return a + b;
}

add(1, 2);      // OK
add('1', '2');  // ← 実行する前にエラーで教えてくれる！

関数の ): number の部分は戻り値の型です。「この関数は必ず数値を返す」と宣言しています。書いておくと、うっかり return を忘れた場合もエラーで気付けます。

全部に型を書く必要はない

最初は「毎回書くのは面倒」と感じるはずです。実は書かなくてよい場面が多い——TypeScriptが自動で推測してくれるからです。これを型推論と呼びます。

let count = 0;          // number だと自動で分かる（書かなくてよい）
let name = '田中';      // string だと分かる

count = "あ";           // ← それでもここでエラーになる

// 一方、引数は推論できないので書く必要がある
function double(n: number) {
  return n * 2;         // 戻り値は number だと推論される
}
💡 書くべき場所は「境界」: 目安は、関数の引数と、外から入ってくるデータです。中の変数はほとんど推論に任せて構いません。型を書く量が減ると、TypeScriptは急に快適になります。

interface — データの形を決める

interface User {
  id: number;
  name: string;
  email: string;
}

function showUser(user: User) {
  console.log(user.name);
  console.log(user.mail);  // ← 「mailは存在しない」と教えてくれる
}

これが特に効くのが、第7章で作ったAPIから返ってくるデータです。どんな形で返ってくるかを1か所に書いておけば、以降は打ち間違いをすべてエディタが止めてくれます。

interface GameRecord {
  id: number;
  winner: string;
  black_count: number;
  white_count: number;
  played_at: string;
  memo?: string;          // ? は「無いかもしれない」
}

async function loadHistory(): Promise<GameRecord[]> {
  const res = await fetch("/api/games");
  return await res.json();
}

const games = await loadHistory();
games[0].black_cnt;    // ← 打ち間違いをその場で指摘してくれる

ユニオン型 — 取りうる値を絞る

冒頭の「黒 / black / くろ」問題を根本から防ぐ書き方があります。取りうる値そのものを型にするのです。

type StoneColor = "black" | "white";     // このどちらか以外は許さない

function putStone(row: number, col: number, color: StoneColor) {
  board[row][col] = color;
}

putStone(3, 4, "black");   // OK
putStone(3, 4, "黒");      // ← エラー。ここで止まる
putStone(3, 4, "Black");   // ← エラー。大文字違いも止まる
📌 これがTypeScriptのいちばん強い使い方: string にしておくと、あらゆる文字列が通ってしまいます。取りうる値が決まっているものは、その値だけを型にする。こうすると、間違った値が入る余地そのものが消えます。手番（"black" | "white"）、マスの状態（0 | 1 | 2）など、オセロには使える場所がたくさんあります。

any — 使うと全部台無しになる型

型エラーに困ったとき、any を書くと黙ります。が、これは型チェックを放棄する宣言です。

let data: any = await res.json();
data.whatever.anything;      // 何を書いてもエラーにならない（実行時に落ちる）

素のJavaScriptで何が大変だったか

第3章で、JavaScriptからDOMを操作しました。オセロを作ったとき、こういうコードを書いたはずです。

// 石を置いたあと、画面を更新する
function updateView() {
  // 64マス全部を見て、盤面の状態と合っているか確認して書き換える
  for (let row = 0; row < 8; row++) {
    for (let col = 0; col < 8; col++) {
      const cell = document.querySelector(`[data-row="${row}"][data-col="${col}"]`);
      cell.className = "";
      if (board[row][col] === 1) cell.classList.add("black");
      if (board[row][col] === 2) cell.classList.add("white");
    }
  }
  // 石数の表示も忘れずに更新
  document.querySelector("#black-count").textContent = countStones(1);
  document.querySelector("#white-count").textContent = countStones(2);
  // 手番の表示も更新
  document.querySelector("#turn").textContent = turn === 1 ? "黒番" : "白番";
}

この方式の問題は、「データを変えたら、画面を変える処理も自分で書かないといけない」ことです。石数の更新を書き忘れれば、盤面だけ変わって数字が古いまま残ります。機能が増えるほど、この「更新し忘れ」が増えていきます。

📌 Reactが解決するのはここ: Reactでは、データ（state）を変えるだけで画面が自動で作り直されます。「画面を更新する処理」を人間が書く必要がなくなる——これがReactを使う最大の理由です。上のような updateView() は、Reactでは1行も書きません。

「どう変えるか」から「どう見えるか」へ

考え方が根本的に変わります。素のJSは「この操作が来たら、画面のここをこう書き換える」という手順の記述でした。Reactは「この状態のとき、画面はこう見える」という結果の記述です。

素のJavaScriptReact

石を置いたら盤面・石数・手番を自分で更新stateを変えるだけ
更新し忘れ起きる起きない（全部stateから作られる）
コードの置き場所HTML・CSS・JSに分かれる部品ごとにまとまる

import { useState } from 'react';

function Counter() {

📌 Reactの考え方: DOMを直接書き換えるのではなく、stateを変えると画面が自動で再描画される。「画面 = stateの反映結果」と考えるのがReactの核心です。document.querySelector を書きたくなったら、それはたいてい設計を見直す合図です。

全員がここで詰まる — stateは直接書き換えない

オセロの盤面をstateにすると、必ずこれを踏みます。「値を変えたのに画面が変わらない」という現象です。

const [board, setBoard] = useState(initialBoard);

// ❌ 直接書き換えても画面は変わらない
board[3][4] = 1;
setBoard(board);       // 中身は変わったが「同じ配列」なのでReactが気付かない

// ⭕ 新しい配列を作って渡す
const next = board.map(row => [...row]);   // 中身ごとコピー
next[3][4] = 1;
setBoard(next);

なぜかというと、Reactは「前の値と違うか」を見て再描画を判断するからです。同じ配列の中身だけ変えても、Reactから見れば「同じもの」なので何も起きません。新しい配列・新しいオブジェクトを作って渡す——これがReactの鉄則です。

⚠️ 2次元配列のコピーは1段では足りない: [...board] だと外側だけの浅いコピーになり、中の各行は元と同じものを指したままです。8×8の盤面では board.map(row => [...row]) のように、行ごとにコピーしてください。ここは第5章のPythonで踏んだ [[0] * 8] * 8 の罠と、実は同じ話です。

リストを描く

盤面の64マスや戦績一覧は、配列から作ります。map で並べるのがReactの定型です。

function Board({ board, onCellClick }) {
  return (
    <div className="board">
      {board.map((row, r) =>
        row.map((cell, c) => (
          <div
            key={`${r}-${c}`}
            className={`cell stone-${cell}`}
            onClick={() => onCellClick(r, c)}
          />
        ))
      )}
    </div>
  );
}

key は、Reactが「どの要素がどれか」を見分けるための目印です。付け忘れると警告が出て、並び替えたときに表示がおかしくなります。配列の添字ではなく、その要素固有の値（戦績なら id）を使うのが望ましい書き方です。

状態をどこに持つか

Reactでいちばん設計が要るのがここです。盤面のstateは、マスの部品ではなく親（盤面全体）が持ちます。

function Game() {
  const [board, setBoard] = useState(initialBoard);
  const [turn, setTurn] = useState("black");

  function handleClick(r, c) {
    const next = board.map(row => [...row]);
    // …裏返し処理…
    setBoard(next);
    setTurn(turn === "black" ? "white" : "black");
  }

  return (
    <div>
      <Board board={board} onCellClick={handleClick} />
      <Score board={board} />
      <Turn turn={turn} />
    </div>
  );
}
📌 これが「状態の持ち上げ」: 石数（Score）も手番（Turn）も、盤面と同じデータを見ています。複数の部品が同じ情報を必要とするなら、共通の親が持って、propsで配る。これがReactの基本的な設計です。「石数表示の更新を忘れる」ことが起きなくなるのは、石数を別で持たず盤面から毎回計算しているからです。

APIからデータを取る — useEffect

第7章で作った戦績一覧を表示します。「画面が表示されたときに1回だけ取ってくる」という処理には useEffect を使います。

import { useState, useEffect } from 'react';

function History() {
  const [games, setGames] = useState([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch("/api/games")
      .then(res => res.json())
      .then(data => { setGames(data); setLoading(false); });
  }, []);        // ← 空の配列 = 最初の1回だけ実行

  if (loading) return <p>読み込み中…</p>;
  return (
    <ul>
      {games.map(g => (
        <li key={g.id}>{g.winner}の勝ち（{g.black_count} - {g.white_count}）</li>
      ))}
    </ul>
  );
}
⚠️ 末尾の [] を忘れると無限ループします: 第2引数の配列は「いつ実行するか」の指定です。[] なら最初の1回だけ。書き忘れると毎回の再描画で実行され、その中でstateを変えるのでまた再描画され…と無限に繰り返します。ブラウザが固まり、サーバに大量のリクエストが飛びます。Networkタブが同じリクエストで埋まっていたら、これを疑ってください。

Q3. propsの説明として正しいものはどれか。

  • CSSのクラス名を管理する仕組み
  • サーバーから取得したJSONの別名
  • 親から子のコンポーネントに渡すデータ
  • コンポーネントが内部で持つ変化する状態
答えと解説

正解: 親から子のコンポーネントに渡すデータ

propsは部品に渡すデータで、同じ部品でも渡す値を変えれば表示が変わる。内部で変化する状態はstateが担当する。

Q4. Reactで画面を更新するときの正しい考え方はどれか。

  • ページ全体を再読み込みする
  • stateを変更すると、その結果として画面が再描画される
  • DOMを直接書き換えて画面を更新する
  • CSSのdisplayを切り替えて表示を変える
答えと解説

正解: stateを変更すると、その結果として画面が再描画される

素のJavaScriptのようにDOMを直接触るのではなく、stateを変えることで画面を変える。「画面=stateの反映結果」と考えるのがReactの発想である。

Q5. Reactでオセロを作るとき、最初にやるべきこととして適切なものはどれか。

  • 画面をどんな部品に分けられるか考える
  • まず全部を1つのコンポーネントに書く
  • CSSを先に完成させる
  • APIの設計から始める
答えと解説

正解: 画面をどんな部品に分けられるか考える

盤面・マス・石数表示・戦績一覧などに分解してから書き始めると設計が楽になる。分解せずに書くと巨大なコンポーネントができて手が付けられなくなる。
