🏗️ HTML

ページの骨組みを作る

🎯 この章のゴール: HTMLが「見た目」ではなく「構造」を書く言語だと理解し、意味に合ったタグを選んでページの骨組みを作れるようになる。最終的にオセロの盤面もHTMLで組みます。

はじめに — 道具をそろえる

本題に入る前に、開発に使う道具を用意します。ここは一度やれば以降ずっと使うものなので、面倒でも最初にきちんと整えてください。必要なのは「エディタ」と「ブラウザ」の2つだけです。

① VS Code を入れる

コードを書くための専用エディタです。メモ帳でも書けますが、色分け・入力補完・エラー表示があるかどうかで学習効率がまるで変わります。現場で最も使われているエディタでもあります。

  1. `Visual Studio Code` で検索し、公式サイトからダウンロードする（無料）
  2. インストーラを実行する。選択肢はすべて既定のままでよい
  3. 起動して、真っ黒な画面が出れば成功

起動したら、拡張機能を入れます。左側の四角が4つ並んだアイコン（Extensions）をクリックし、名前で検索してインストールしてください。

拡張機能何ができるか必須度
Japanese Language PackVS Code のメニューが日本語になる好みで
Live Server保存すると自動でブラウザが更新されるほぼ必須
HTML CSS SupportHTMLの中でCSSクラス名を補完してくれるあると楽
📌 Live Server がいちばん効く: これを入れると、HTMLファイルを右クリック →「Open with Live Server」で開けます。以降はファイルを保存するだけでブラウザが自動更新されるので、「保存 → ブラウザに切り替え → 再読み込み」の繰り返しが不要になります。地味ですが学習速度がかなり変わります。

② 作業フォルダを作る

作ったファイルが散らからないよう、専用のフォルダを決めます。日本語やスペースを含まない場所にするのが無難です（後々ツールが誤動作する原因になります）。

C:\dev\web-study\          ← ここを作業フォルダにする
  ├─ profile.html          ← 第1章で作る
  ├─ style.css             ← 第2章で追加
  └─ script.js             ← 第3章で追加

フォルダを作ったら、VS Code の「ファイル → フォルダーを開く」でそのフォルダを開いてください。左側にファイル一覧が出れば準備完了です。

⚠️ 拡張子を表示させておく: Windowsは初期設定で拡張子（.html などの末尾）を隠します。この状態で作業すると 「profile.html」のつもりが「profile.html.txt」になっていて開けないという事故が起きます。 エクスプローラーの「表示」タブ →「ファイル名拡張子」にチェックを入れて、必ず表示させてください。

③ ブラウザと開発者ツール

ブラウザは Chrome か Edge を使ってください。どちらも同じ仕組みで動いており、開発者向けの機能が充実しています。

準備できたら、いま見ているこのページで F12キー を押してみてください。画面が分割されて、コードのようなものが出れば成功です。これが開発者ツールで、この先ずっと使います（詳しい使い方はこの章の後半で説明します）。

💡 これで準備完了: 道具はこれだけです。Web開発は最初の一歩の敷居が低いのが良いところで、エディタとブラウザさえあれば始められます。Gitやサーバは必要になったときに入れます（第4章・第5章）。

そもそもWebページとは何でできているか

普段見ているWebページは、実はただのテキストファイルです。ブラウザがそのテキストを読んで、解釈して、画面に描いています。魔法は何もありません。

そのテキストは3種類の役割に分かれています。この分担がWeb開発の土台なので、最初に頭に入れてください。

言語役割例えるなら
HTML構造（何がどこにあるか）家の骨組み・間取り
CSS見た目（どう見えるか）内装・壁紙・家具の配置
JavaScript動き（何が起きるか）電気・水道などの設備

この章で扱うのはHTMLだけです。見た目が地味でも気にしないでください。骨組みが正しくできていれば、あとから内装はいくらでも変えられます。

最小のHTMLファイル

まずは動くものを見ます。テキストエディタで次を書いて `index.html` という名前で保存し、ダブルクリックしてブラウザで開いてください。

<!DOCTYPE html>
<html lang="ja">
  <head>
    <meta charset="UTF-8">
    <title>はじめてのページ</title>
  </head>
  <body>
    <h1>こんにちは</h1>
    <p>これが最初のWebページです。</p>
  </body>
</html>

表示されましたか。これでもうWebページを作ったことになります。順に何を書いたか見ていきます。

  • `<!DOCTYPE html>` … 「これはHTMLです」という宣言。おまじないと思ってよい。必ず1行目に書く
  • `<html lang="ja">` … 全体を包む要素。lang="ja" は日本語のページだという情報
  • `<head>` … ページの設定を書く場所。画面には表示されない
  • `<meta charset="UTF-8">` … 文字コードの指定。これが無いと日本語が文字化けする
  • `<title>` … ブラウザのタブに出る名前
  • `<body>` … 実際に画面に表示される中身。ここが本体
⚠️ 文字化けしたら: 日本語が「譁�蟄怜喧縺�」のように壊れて見えたら、ほぼ `<meta charset="UTF-8">` の書き忘れです。ファイル自体の保存形式がUTF-8になっているかも確認してください（VS Codeなら右下に表示されます）。

要素とタグ — HTMLの基本単位

HTMLは要素の積み重ねでできています。要素は「開始タグ」「中身」「終了タグ」の3つで1組です。

<p>これが段落です。</p>
↑            ↑        ↑
開始タグ     中身     終了タグ（/ が付く）

終了タグを忘れると、そこから後ろが全部おかしくなります。慣れるまでは開始タグを書いたらすぐ終了タグも書いて、後から中身を埋めるやり方が安全です。

入れ子（ネスト）— 箱の中に箱を入れる

要素の中に別の要素を入れられます。これを入れ子と呼びます。HTMLの構造はすべてこの入れ子でできています。

<ul>
  <li>じゃがいも</li>
  <li>にんじん</li>
  <li>玉ねぎ</li>
</ul>
⚠️ 閉じる順番は「後に開けたものを先に閉じる」: 箱を入れ子にするのと同じで、順番を守らないと壊れます。 ⭕ 正しい: <p>これは<strong>大事</strong>です</p> ❌ 誤り: <p>これは<strong>大事</p></strong>
💡 インデントを付ける: 入れ子になったら、中の要素は半角スペース2つ分ずらして書きます。ブラウザの動作には影響しませんが、人間が読むときに構造が一目で分かります。これは実務でも必ず守られている習慣です。

属性 — 要素に情報を足す

タグには属性という追加情報を書けます。「開始タグの中に、名前=\"値\" の形で書く」と覚えてください。

<a href="https://example.com">リンクの文字</a>
   ↑    ↑
   属性名 値（ダブルクォートで囲む）

<img src="cat.jpg" alt="猫の写真">
<div id="board" class="game-area">…</div>
属性使うタグ意味
hrefaリンク先のURL
srcimg画像ファイルの場所
altimg画像が表示できないときの代替文。読み上げにも使われる
idどの要素にもその要素だけの名前。ページ内で重複させない
classどの要素にもグループ名。同じclassを複数の要素に付けてよい
📌 id と class は後で効いてくる: いまは「名前を付けるもの」という理解で十分です。ただし次章のCSSと第3章のJavaScriptで多用します。CSSは「この名前の要素をこう見せる」、JavaScriptは「この名前の要素を操作する」ために使います。ここで名前を付ける習慣をつけておくと後が楽です。

まず覚えるタグ

HTMLのタグは100種類以上ありますが、実際によく使うのは20個程度です。まずは次のものから覚えてください。

タグ意味補足
h1〜h6見出しh1が最上位。1ページにh1は1つが基本
p段落文章のかたまり
ul / li順序なしリスト黒丸のリスト。liはulの中にだけ書く
ol / li順序つきリスト番号が振られる
aリンクhref属性で行き先を指定
img画像終了タグが無い（中身を持たないため）
table表オセロの盤面にも使える
buttonボタン押せる要素。JSと組み合わせる
input入力欄終了タグが無い
div意味を持たない箱グループ化のための入れ物
span意味を持たない箱（文中用）文章の一部を囲むとき

div と span の違い

初心者がよく混乱する2つです。役割は同じ「意味を持たない箱」ですが、表示のされ方が違います。

  • div … 前後で改行される（縦に積まれる）。ブロック要素と呼ぶ
  • span … 改行されず、文章の中に収まる。インライン要素と呼ぶ
<div>これは箱1</div>
<div>これは箱2</div>
<!-- → 縦に2段で表示される -->

<p>この文の<span>ここだけ</span>を囲む</p>
<!-- → 1行のまま。spanは流れを乱さない -->

「見た目」でタグを選んではいけない

ここがこの章でいちばん大事な話です。「文字を大きくしたいからh1を使う」という選び方をしないでください。h1は「このページの主題」を表すタグであって、文字を大きくするタグではありません。

❌ 悪い例（見た目で選んでいる）
<h1>会社概要</h1>
<h1>お問い合わせ</h1>     ← 大きくしたいから h1 にした

⭕ 良い例（意味で選んでいる）
<h1>株式会社サンプル</h1>  ← ページの主題は1つ
<h2>会社概要</h2>
<h2>お問い合わせ</h2>

意味に合ったタグを選ぶことをセマンティックなHTMLと言います。なぜ大事かというと、HTMLを読むのは人間の目だけではないからです。

  • 検索エンジン … h1やタグ構造を見てページの内容を理解する。検索結果での見え方が変わる
  • スクリーンリーダー … 目の不自由な人が使う読み上げソフト。「見出しだけ拾って移動」ができるのは h1〜h6 が正しく付いているページだけ
  • あとで直す人 … 下の例を見てください

3つ目が分かりにくいので、具体例を出します。次の2つは画面上はまったく同じに見えます。半年後にこのコードを開いて、どこを直せばいいか分かるのはどちらでしょうか。

❌ 全部 div で書いた場合
<div class="t1">料金プラン</div>
<div class="b1">
  <div class="t2">無料プラン</div>
  <div class="x">月0円</div>
</div>

⭕ 意味のあるタグで書いた場合
<h2>料金プラン</h2>
<section>
  <h3>無料プラン</h3>
  <p>月0円</p>
</section>

上は `t1` `b1` `x` が何なのか、CSSを開いて照らし合わせないと分かりません。下は読むだけで「料金プランの見出しがあって、その下に無料プランの説明がある」と分かります。半年後の自分は他人です。そのとき助かるのは下の書き方です。

💡 判断に迷ったときの問い: 「CSSを全部外したとき、この文書は読めるか」を考えてみてください。見出し・段落・リストが適切なら、装飾ゼロでも意味が通ります。通らないなら、タグの選び方を見直す合図です。

なぜ「構造」と「見た目」を分けるのか

実はHTMLにも文字を大きくしたり色を変えたりするタグ（`<font>` など）が存在します。ですがもう使われません。構造と見た目を混ぜると、後から変更するのが地獄になるからです。

例えば100ページのサイトで「見出しの色を変えたい」となったとき——構造と見た目が分かれていればCSSの1行を直すだけで全ページに反映されます。混ざっていると、100ページ分の全見出しを手作業で直すことになります。この差は決定的です。

開発者ツールを開いてみる

ブラウザには、表示中のページのHTMLを見る機能が標準で付いています。世の中の全Webページが教材になるので、必ず使えるようになってください。

  1. 好きなWebページを開く
  2. 気になる部分を右クリック →「検証」（または F12）
  3. 画面が分割され、そのページのHTMLが表示される
  4. HTMLの行にマウスを乗せると、画面上の対応する場所が光る
💡 使い方のコツ: 「このボタン、どう作られているんだろう」と思ったら右クリック→検証。プロが書いたHTMLをいくらでも読めます。最初は複雑で面食らいますが、知っているタグを探すだけでも勉強になります。

🛠 課題: プロフィールカード（第1段階）

自分のプロフィールカードをHTMLだけで作ります。この課題は第2章・第3章で育てていくので、消さずに取っておいてください。見た目は次章で整えるので、いまは構造だけに集中します。

作るもの

  1. `profile.html` を作り、DOCTYPE から body までの骨組みを書く
  2. タブに表示される title を自分の名前にする
  3. 名前を h1、肩書き（学習中のことなど）を p で書く
  4. 「できること」を ul のリストで3つ以上書く
  5. 好きなサイトへのリンクを a で貼る（新しいタブで開く方法も調べてみる）
  6. 自己紹介文を p で2〜3段落書く
  7. 各パーツを div で囲み、id か class で名前を付けておく（次章で使う）
  8. ブラウザで開いて表示を確認し、開発者ツールで構造を見る

文字化けしていない
h1 が1つだけになっている

📝 確認クイズ

Q1. HTMLの役割として最も適切なものはどれか。

  • ページの構造（骨組み）を記述する
  • ページの見た目を装飾する
  • ページに動きをつける
  • データベースを操作する
答えと解説

正解: ページの構造（骨組み）を記述する

正しくは「ページの構造（骨組み）を記述する」。構造はHTML・見た目はCSS・動きはJavaScriptと役割が分かれている。

Q2. ページ内で最上位の見出しを表すHTMLタグはどれか。

  • p
  • div
  • span
  • h1
答えと解説

正解: h1

見出しはh1〜h6で表しh1が最上位。1ページにh1は1つが基本である。pは段落・div/spanは意味を持たないグループ化の入れ物。

Q3. 次のうち、入れ子の閉じ方が正しいものはどれか。

  • <p>これは<strong>大事です</p>
  • <strong><p>これは大事</strong></p>
  • <p>これは<strong>大事</strong>です</p>
  • <p>これは<strong>大事</p></strong>
答えと解説

正解: <p>これは<strong>大事</strong>です</p>

入れ子は「後に開けたものを先に閉じる」のが原則。順番が入れ替わると表示が崩れる原因になる。

Q4. div と span の違いとして正しいものはどれか。

  • divは前後で改行されるが、spanは文章の流れの中に収まる
  • divは見出し用、spanは段落用である
  • divは文字を大きく、spanは小さく表示する
答えと解説

正解: divは前後で改行されるが、spanは文章の流れの中に収まる

divはブロック要素で縦に積まれ、spanはインライン要素で改行されない。どちらも意味を持たない入れ物という点は同じ。

見た目とレイアウトを整える

🎯 この章のゴール: セレクタでHTML要素を選んでスタイルを当てる仕組みを理解し、Flexboxで簡単なレイアウトを組めるようになる。

CSSとは何か

CSS（Cascading Style Sheets）は、HTMLで作った骨組みに見た目（色・大きさ・配置）を与える言語です。「どの要素に」「どんなスタイルを」の2つをセットで書きます。

/* セレクタ { プロパティ: 値; } */
h1 {
  color: #1e3a8a;
  font-size: 2rem;
}
.card {          /* class="card" の要素に当たる */
  padding: 16px;
  border-radius: 8px;
}

セレクタの基本

  • h1 … タグ名で選ぶ
  • .card … class属性で選ぶ（先頭にドット）。最もよく使う
  • #header … id属性で選ぶ（先頭にシャープ）

ボックスモデル

すべての要素は箱（ボックス）として描画されます。内側から content → padding → border → margin の層になっていて、レイアウト崩れの原因の大半はここの理解不足です。

Flexboxで並べる

.row {
  display: flex;        /* 子要素を横に並べる */
  gap: 12px;            /* 要素間の隙間 */
  justify-content: center;  /* 水平方向の揃え */
  align-items: center;      /* 垂直方向の揃え */
}
💡 コツ: 開発者ツールで要素を選ぶと、ボックスモデル（padding / margin）が色付きで表示されます。「なぜズレるのか」は目で見て確認するのが最短です。

CSSファイルを分ける

CSSはHTMLの中に直接書くこともできますが、別ファイルにして読み込むのが基本です。こう書きます。

<!-- profile.html の <head> の中 -->
<link rel="stylesheet" href="style.css">
📌 なぜ分けるのか: 前章で「構造と見た目を分ける」と言いました。ファイルまで分けると、その恩恵がはっきりします。1つのCSSファイルを複数のページで使い回せるので、サイト全体の見た目を1か所で変えられます。逆にHTMLに直接書くと、ページが増えるたび同じ指定をコピーすることになります。

🛠 課題: プロフィールカード（第2段階 — 見た目を整える）

第1章で作った profile.html に、外部CSSファイルでスタイルを当てます。HTMLファイルは構造だけ、見た目は全部CSSファイル、という分担を体験するのが狙いです。

作るもの

  1. `style.css` を作り、profile.html から link で読み込む
  2. カード風の見た目にする（背景色・padding・border-radius・box-shadow）
  3. 名前と肩書きで文字サイズや色に差をつけ、情報の優先順位を表現する
  4. Flexbox を使って、リストの項目を横並びのタグ風にする
  5. HTMLファイルには style 属性を1つも書かない

できたと言える条件

style.css を削除すると、見た目だけが消えて内容は残る
HTMLに style="..." が1つも書かれていない

💡 「HTMLを見て構造が、CSSを見て見た目が分かる」状態が理想です。迷ったら、その要素が「何であるか」はHTML、「どう見えるか」はCSSと考えます。

JavaScriptとは何か

JavaScriptは、ページに動き（ロジック）を与えるプログラミング言語です。「ボタンを押したら表示を変える」「入力内容をチェックする」など、ユーザーの操作に反応する部分を担当します。

基本文法

const name = '田中';            // 変数（再代入しないなら const）
let count = 0;                  // 再代入するなら let

if (count > 10) {               // 条件分岐
  console.log('多いですね');
} else {
  console.log('まだ少ない');
}

const fruits = ['りんご', 'みかん', 'バナナ'];  // 配列
for (const f of fruits) {       // 繰り返し
  console.log(f);
}

function greet(who) {           // 関数
  return 'こんにちは、' + who + 'さん';
}

DOM操作 — HTMLとつなぐ

const btn = document.querySelector('#myButton');
btn.addEventListener('click', () => {
  document.querySelector('#message').textContent = '押されました！';
});
⚠️ ここが本番: JavaScriptからは必ずエラーに出会います。エラーが出たら「エラー文を読む → 原因の仮説を立てる → 調べる → 修正する」。この流れを毎回意識してください。エラー文はコンソール（開発者ツールのConsoleタブ）に出ます。
💡 コツ: 困ったらまず console.log() で変数の中身を表示して確認する癖をつけましょう。「思っていた値と違う」がバグの正体であることがほとんどです。

JSファイルも分ける

CSSと同じで、JavaScriptも別ファイルにします。`</body>` の直前で読み込むのが基本です。

<!-- profile.html の </body> の直前 -->
<script src="script.js"></script>
📌 3つの役割がそろった: これで HTML（構造）・CSS（見た目）・JavaScript（動き） の3ファイル構成になります。この分け方はWeb開発の基本形で、どんな大きなサイトも根っこは同じです。「どのファイルを直せばいいか」が明確になるのが最大の利点です。

第4章 · vcs

🌿 Git

履歴を残し、2人でオセロを作る

🎯 この章のゴール: 5つの基本コマンドでコードをGitHubに置けるようになり、2人で1つのリポジトリを共有してオセロを完成させる。技術より「進め方」を身につけるのが本当の目的。

なぜ今Gitを学ぶのか

Gitはコードの変更履歴を記録する道具です。TypeScriptやReactより先に学ぶのは、実際の開発では早い段階からGitを使う習慣をつけたほうが自然だからです。ここから先の演習はすべてGitで履歴を残しながら進めます。

まず覚える5コマンド

git clone <URL>     # リモートのリポジトリを手元に複製する
git add .           # 変更をステージに載せる（コミット対象にする）
git commit -m "メッセージ"   # 変更を履歴として記録する
git push            # 手元の履歴をGitHubに送る
git pull            # GitHubの最新を手元に取り込む

日々の流れは「書く → add → commit → push」の繰り返しです。この5つだけで十分。branchやrebaseは後回しで構いません（チーム開発に入る段階で学びます）。

💡 コツ: commitメッセージは「何をしたか」を短く書きます（例:「カウンター機能を追加」）。1日の終わりにまとめて1回ではなく、キリのいい単位でこまめにcommitするのがおすすめです。
⚠️ 注意: パスワードやAPIキーを書いたファイルをcommitしないこと。一度pushした履歴は簡単には消せません。秘密情報は .gitignore で除外します。

✏️ 練習

まず1人で慣れます。GitHubにリポジトリを作り、前章までのプロフィールカード（HTML・CSS・JSの3ファイル）をpushしてみましょう。3回以上commitを分けて、GitHub上で履歴が見えることを確認します。

ここからが本番 — 2人で1つのものを作る

ここまでは1人で作ってきました。ここからは2人で1つのリポジトリを共有してオセロを作ります。これがこのコース最大の山場であり、いちばん面白いところです。

📌 なぜオセロなのか: オセロはHTML・CSS・JavaScriptだけで完成させられます。新しい技術を覚える必要がなく、ここまでの知識だけで「ちゃんと遊べるもの」が作れる。だから技術ではなく進め方に集中できます。

いきなり書き始めない — まず機能に分解する

「オセロを作ろう」と言われても、どこから手をつけるか分かりません。実務でも同じで、まず何が必要かを洗い出して、小さな単位に割るところから始めます。これを機能分解と呼びます。

2人で話し合って、オセロに必要な機能を挙げてください。以下は例です。この表を鵜呑みにせず、自分たちで考えることが課題の本体です。

機能やること難しさ
盤面を表示する8×8のマス目をHTML/CSSで作る易
石を置くクリックしたマスに石を表示する易
手番を管理する黒→白→黒…と交互に切り替える易
裏返す判定8方向を調べ、挟んだ石を裏返す難
置ける場所の判定裏返せる場所にしか置けないようにする難
パス処理置ける場所が無いとき手番を飛ばす中
勝敗判定全マス埋まったら石を数えて勝敗を出す中

💡 分解のコツ: 「1つの機能 = 半日〜1日で終わる大きさ」を目安にします。大きすぎると進捗が見えず、小さすぎると管理が面倒になります。難しさも一緒に見積もっておくと、後の分担が楽になります。

分担と順番を決める

機能が並んだら、どれから作るかと誰がやるかを決めます。順番のコツは「まず動く最小限を作る」こと。裏返し判定のような難所から始めると、何も動かない期間が長くなって心が折れます。

  1. 第1週: 盤面表示 + 石を置く（クリックしたら石が出る。ルールは無視）
  2. 第2週: 手番の切り替え + 石数表示（交互に置けるようになる）
  3. 第3週: 裏返し判定（ここが山。8方向のロジック）
  4. 第4週: 置ける場所の制限 + パス + 勝敗判定（ゲームとして完成）
⚠️ 同じファイルを2人で触ると衝突する: 2人が同時に同じ行を変更してpushすると、Gitが「どちらを採用すべきか分からない」と止まります（コンフリクト）。これは事故ではなく正常な動作です。慌てず、2人で画面を見ながらどちらを残すか決めれば直せます。分担するとき、なるべく担当ファイルを分けておくと衝突は減ります。

進捗を見える形にする

GitHubには Issues（課題の一覧）という機能があります。分解した機能を1つずつIssueとして登録すると、「今どれをやっているか」「どこまで終わったか」が2人で共有できます。終わったらIssueを閉じる。これだけで進捗管理になります。

🛠 課題: オセロを2人で作る

共同リポジトリでオセロを完成させます。技術的な目的はGitの共同作業に慣れることですが、本当のゴールは「大きなものを小さく割って、順番に片付ける」進め方を体で覚えることです。

  1. 2人で1つのGitHubリポジトリを作り、両方がpushできるようにする（Collaborator に追加）

  3. どれから作るか順番を決め、担当を分ける
  4. 週ごとに区切って進める。毎回こまめにcommit・pushする
  5. 相手のコードを読み、気付いたことを伝え合う
  6. 完成したら2人で対戦してみる

できたと言える条件

コンフリクトを最低1回は経験し、自力で解決した

サーバ側の言語を覚える

🎯 この章のゴール: Pythonの基本文法を身につけ、JavaScriptで書ける処理をPythonでも書ける状態になる。次章以降でサーバを書くための土台を作る。

なぜここで別の言語を学ぶのか

ここまで作ったオセロは、すべてブラウザの中だけで動いています。ページを閉じれば対戦結果は消え、他の人と共有もできません。「戦績を保存する」「ユーザーを作る」には、ブラウザの外——サーバが必要です。

サーバを書く言語はいくつもあり、JavaScriptでも書けます。ここでPythonを選ぶのは、文法が読みやすく、Web以外（データ処理・AI）でも使えるからです。1つ目の言語を覚えた後に2つ目を学ぶと、「言語が違っても考え方は同じ」だと分かります。これは大きな収穫です。

📌 ここが最初の大きな壁: ブラウザの中（フロントエンド）とサーバ（バックエンド）は別の場所で動く別のプログラムです。この2つがどう繋がるかが分かると、Webアプリの全体像が見えます。焦らず進めてください。

JavaScriptと比べてみる

まずは同じ処理を並べます。似ている部分が多いことに気付くはずです。

// JavaScript
const name = "田中";
let count = 0;

if (count > 10) {
  console.log("多い");
} else {
  console.log("少ない");
}

const fruits = ["りんご", "みかん"];
for (const f of fruits) {
  console.log(f);
}

function greet(who) {
  return "こんにちは、" + who;
}
# Python
name = "田中"
count = 0

if count > 10:
    print("多い")
else:
    print("少ない")

fruits = ["りんご", "みかん"]
for f in fruits:
    print(f)

def greet(who):
    return "こんにちは、" + who

決定的な違い — インデントがブロックを決める

JavaScriptは波括弧 `{ }` で処理のまとまりを表しますが、Pythonは行頭の空白（インデント）でそれを表します。波括弧もセミコロンもありません。

def check(n):
    if n > 0:
        print("正の数")
        print("この2行はif の中")
    print("この行はif の外（関数の中）")
print("この行は関数の外")
⚠️ 最初はここで必ず詰まる: インデントがずれると `IndentationError` というエラーになります。エラーが出たらまず行頭の空白を疑ってください。スペース4つで揃えるのが慣習です。エディタの設定でタブとスペースが混ざると厄介なので、VS Codeの設定を確認しておきましょう。

リストと辞書

JSの配列がPythonではリスト、JSのオブジェクトが辞書にあたります。オセロの盤面や戦績を扱うときに使います。

# リスト（JSの配列）
scores = [10, 25, 8]
scores.append(30)        # 追加（JSのpush）
print(len(scores))       # 個数（JSのlength）

# 辞書（JSのオブジェクト）
player = {"name": "田中", "wins": 3}
print(player["name"])    # 田中
player["wins"] = 4       # 更新

# 辞書のリスト（戦績データはこんな形になる）
records = [
    {"winner": "黒", "black": 38, "white": 26},
    {"winner": "白", "black": 20, "white": 44},
]
for r in records:
    print(r["winner"], r["black"], "-", r["white"])

第6章 · backend

🗃️ SQL

データの置き場所を設計する

🎯 この章のゴール: オセロの戦績を保存するテーブルを自分で設計できるようになる。あわせてSQLの基本操作を覚え、データの出し入れができるようにする。

なぜデータベースが要るのか

前章でPythonを覚えましたが、プログラムの中の変数は実行が終われば消えます。オセロの対戦結果を後から見返したいなら、どこかに書き残さないといけません。その置き場所がデータベース（DB）です。

「ファイルに書けばいいのでは」と思うかもしれません。実際できます。ただ、探す・並べ替える・複数人が同時に書くといったことをファイルでやると大変です。DBはそれを得意とする専用の道具です。

テーブル = 表

DBの中では、データをテーブルという表の形で持ちます。Excelのシートを思い浮かべてください。列（どんな項目か）と行（1件ずつのデータ）でできています。

idwinnerblack_countwhite_countplayed_at
1黒38262026-08-01 14:30
2白20442026-08-01 15:10
3引き分け32322026-08-02 09:05
📌 設計でいちばん大事な問い: 「この表の1行は、何を表しているのか」 を一言で言えるようにすること。上の表なら「1行 = 1回の対戦」です。これが曖昧なまま作ると、後で必ず破綻します。

列には型を決める

各列には「どんな種類のデータが入るか」（型）を決めます。数値の列に文字を入れようとするとDBが拒否してくれるので、おかしなデータが混ざるのを防げます。

CREATE TABLE games (
  id           INTEGER PRIMARY KEY,   -- 主キー。行を特定する
  winner       TEXT NOT NULL,         -- 文字。空は許さない
  black_count  INTEGER NOT NULL,      -- 整数
  white_count  INTEGER NOT NULL,
  played_at    TIMESTAMP DEFAULT NOW() -- 日時。既定は今
);
  • INTEGER … 整数
  • TEXT … 文字列
  • BOOLEAN … true / false
  • TIMESTAMP … 日時
  • PRIMARY KEY … その行を特定する列。重複できない
  • NOT NULL … 空を許さない

4つの基本操作（CRUD）

-- Create: 追加する
INSERT INTO games (winner, black_count, white_count)
VALUES ('黒', 38, 26);

-- Read: 取り出す
SELECT * FROM games;                          -- 全部
SELECT * FROM games WHERE winner = '黒';      -- 条件つき
SELECT * FROM games ORDER BY played_at DESC;  -- 新しい順
SELECT * FROM games ORDER BY played_at DESC LIMIT 5;  -- 直近5件

-- Update: 書き換える
UPDATE games SET winner = '白' WHERE id = 1;

-- Delete: 消す
DELETE FROM games WHERE id = 1;
⚠️ WHERE を忘れると全部消える: `DELETE FROM games;` と書くと全行が消えます。`UPDATE` も同じで、WHERE無しだと全行が書き換わります。実務でもっとも怖い事故のひとつです。DELETE や UPDATE を書くときは、先に同じ条件で SELECT して対象を確認する癖をつけてください。

表を分ける — 外部キー

「誰が対戦したか」も残したくなったとします。プレイヤー名を games テーブルに直接書くこともできますが、名前が変わったとき全行を直すことになります。そこで表を分けて、繋ぐという考え方を使います。

CREATE TABLE players (
  id    INTEGER PRIMARY KEY,
  name  TEXT NOT NULL
);

CREATE TABLE games (
  id            INTEGER PRIMARY KEY,
  black_player  INTEGER REFERENCES players(id),  -- 外部キー
  white_player  INTEGER REFERENCES players(id),
  winner        TEXT NOT NULL,
  black_count   INTEGER NOT NULL,
  white_count   INTEGER NOT NULL,
  played_at     TIMESTAMP DEFAULT NOW()
);

games には名前ではなくプレイヤーのidを持たせます。こうすると名前を変えたいとき players を1行直すだけで済みます。

繋いで取り出す — JOIN

表を分けると、取り出すときに繋ぎ直す必要があります。それが JOIN です。

SELECT
  g.id,
  b.name AS black_name,
  w.name AS white_name,
  g.winner,
  g.played_at
FROM games g
JOIN players b ON g.black_player = b.id
JOIN players w ON g.white_player = w.id
ORDER BY g.played_at DESC;
💡 まずは分けずに作ってもいい: 最初から完璧な設計を目指すと進みません。1つのテーブルで作ってみて、不便を感じてから分けるほうが、なぜ分けるのかが腹落ちします。実際の開発でも設計は途中で変わります。

🔌 API

ブラウザとサーバをつなぐ

🎯 この章のゴール: FastAPIでサーバを立て、オセロの画面から戦績を送って一覧を取得できるようにする。ブラウザとサーバが別プログラムとして動いていることを、目で見て確認する。

いま2つのプログラムがある

ここまでで、ブラウザで動くオセロ（HTML/CSS/JS）と、Pythonで書いたコード、そしてデータベースができました。これらはそれぞれ別の場所で動く、別のプログラムです。

[ブラウザ]              [サーバ]
HTML/CSS/JS      ？      Python + DB
オセロの画面     ←→      戦績の保存先

この「？」の部分をつなぐのが API

ブラウザのJavaScriptから、サーバのPythonの関数を直接呼ぶことはできません。間にHTTPという約束事を挟んで、JSONという形式でデータをやり取りします。その窓口がAPIです。

窓口の作り方 — URLとメソッド

APIは「どのURLに」「どの方法で」アクセスするかで機能が決まります。

メソッドURLやること
GET/api/games戦績の一覧を取得する
POST/api/games対戦結果を1件追加する
GET/api/games/33番の対戦の詳細を取得する
DELETE/api/games/33番の対戦を削除する
💡 前章とのつながり: この4つは、SQLで学んだ CRUD（INSERT / SELECT / UPDATE / DELETE）ときれいに対応します。APIは「外から使えるようにしたCRUD」だと考えると分かりやすくなります。

FastAPIでサーバを書く

PythonでAPIを作るライブラリはいくつかありますが、ここでは FastAPI を使います。書く量が少なく、自動でAPIの説明ページを作ってくれるのが大きな利点です。

# main.py
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

🗄️ DB連携

サーバからデータを保存する

🎯 この章のゴール: 前章のAPIをDBに繋ぎ、サーバを再起動しても戦績が残る状態にする。Webアプリの3層構成を自分の言葉で説明できるようになる。

全体像がつながる

ここまでに作ったものが、いよいよ1本につながります。

[ブラウザ]          [サーバ]              [DB]
オセロの画面   →    FastAPI        →    games テーブル
HTML/CSS/JS   ←    Python         ←    players テーブル

  fetch()          エンドポイント        SQL

この3層の絵が描ければ、Webアプリの基本は理解できたと言えます。APIがブラウザとDBの橋渡しをしている——これがいちばん大事な理解です。

PythonからDBに繋ぐ

まずは生のSQLで動かします。SQLiteなら追加のインストールも要りません。

# db.py
import sqlite3

def get_conn():
    conn = sqlite3.connect("othello.db")
    conn.row_factory = sqlite3.Row   # 辞書のように使えるようにする
    return conn

def init_db():
    conn = get_conn()
    conn.execute("""
        CREATE TABLE IF NOT EXISTS games (
          id          INTEGER PRIMARY KEY AUTOINCREMENT,
          winner      TEXT NOT NULL,
          black_count INTEGER NOT NULL,
          white_count INTEGER NOT NULL,
          played_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        )
    """)
    conn.commit()
    conn.close()

APIをDBに繋ぎ替える

前章では戦績をリスト（メモリ）に入れていました。そこをDBの読み書きに置き換えます。

# main.py
@app.get("/api/games")
def list_games():
    conn = get_conn()
    rows = conn.execute(
        "SELECT * FROM games ORDER BY played_at DESC"
    ).fetchall()
    conn.close()
    return [dict(r) for r in rows]

@app.post("/api/games")
def add_game(game: Game):
    conn = get_conn()
    conn.execute(
        "INSERT INTO games (winner, black_count, white_count) VALUES (?, ?, ?)",
        (game.winner, game.black_count, game.white_count),   # ← 値は別で渡す
    )
    conn.commit()
    conn.close()
    return {"ok": True}
📌 ここが本章のハイライト: この状態でサーバを再起動してから一覧を見てください。データが残っているはずです。前章までは消えていました。この違いが「保存する」ということです。

絶対にやってはいけない書き方

上のコードで、値を `?` で書いて別に渡しているのには理由があります。もし文字列を繋げて書くと、入力次第でSQLを乗っ取られます。

# ❌ 絶対にダメな書き方
name = 受け取った値
conn.execute("SELECT * FROM players WHERE name = '" + name + "'")

# もし name に  ' OR '1'='1  が入ったら、実行されるSQLは
# SELECT * FROM players WHERE name = '' OR '1'='1'
# → 全件が返ってくる（条件が無意味になる）

# もっと悪いと  '; DROP TABLE games; --  で表ごと消される
# ⭕ 正しい書き方（プレースホルダを使う）
conn.execute("SELECT * FROM players WHERE name = ?", (name,))
⚠️ SQLインジェクション: これは実際に起き続けている代表的な攻撃です。「自分のアプリは小さいから大丈夫」ということはありません。ユーザーからの入力をSQLに文字列連結しない——これだけは例外なく守ってください。

ORM — SQLをコードで書く

生SQLで仕組みが分かったら、ORMという道具に進めます。SQLをPythonのコードとして書けるようになり、プレースホルダも自動で使われるので安全です。

# SQLAlchemy を使った例
games = session.query(Game).order_by(Game.played_at.desc()).all()

session.add(Game(winner="黒", black_count=38, white_count=26))
session.commit()
💡 なぜ生SQLを先にやったか: ORMは便利ですが、中で何が起きているか分からないまま使うと詰まったとき何もできません。生SQLを知っていれば「ORMがどんなSQLを出しているか」を確認して原因を追えます。順番が大事です。

🎯 この章のゴール: 「型があると実行する前に間違いに気付ける」価値を体感し、基本の型注釈とinterfaceを書けるようになる。

TypeScriptとは何か

TypeScriptは、JavaScriptに型を追加した言語です。書いたコードはJavaScriptに変換されて動きます。つまり「JavaScriptの上位互換」で、これまで学んだ文法はそのまま使えます。

型注釈の基本

let count: number = 0;
let name: string = '田中';
let done: boolean = false;
let tags: string[] = ['html', 'css'];

function add(a: number, b: number): number {
  return a + b;
}

add(1, 2);      // OK
add('1', '2');  // ← 実行する前にエラーで教えてくれる！

interface — データの形を決める

interface User {
  id: number;
  name: string;
  email: string;
}

function showUser(user: User) {
  console.log(user.name);
  console.log(user.mail);  // ← 「mailは存在しない」と教えてくれる
}
📌 なぜ型が大事か: JavaScriptだけだと、間違いは実行して初めて分かります。TypeScriptなら書いた瞬間にエディタが教えてくれる。バグ探しの時間が大幅に減り、あとで学ぶReactやAPI連携でも「データの形」が明確になります。

オセロを部品で組み直す（発展）

🎯 この章のゴール: コンポーネント・props・state の3つを理解し、部品を組み合わせて画面を作れるようになる。

Reactとは何か

Reactは、画面をコンポーネント（部品）として分割して組み立てるライブラリです。「ボタン」「カード」「一覧」を部品として作り、組み合わせて画面にします。部品は再利用できるので、大きなアプリでも整理された状態を保てます。

コンポーネントとJSX

function Hello(props) {
  return <h1>こんにちは、{props.name}さん</h1>;
}

function App() {
  return (
    <div>
      <Hello name="田中" />
      <Hello name="佐藤" />
    </div>
  );
}

HTMLに似た書き方（JSX）でコンポーネントの見た目を書きます。propsは部品に渡すデータです。同じ部品でも渡すpropsを変えれば表示が変わります。

state — 画面が変わる仕組み

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      {count} 回押しました
    </button>
  );
}
📌 Reactの考え方: DOMを直接書き換えるのではなく、stateを変えると画面が自動で再描画される。「画面 = stateの反映結果」と考えるのがReactの核心です。
💡 コツ: 迷ったら「この画面はどんな部品に分けられるか？」から考えます。ヘッダー・一覧・一覧の1行・ボタン…と分解してから作り始めると設計が楽になります。

  4. マスをクリックしたら state を更新し、画面が自動で変わることを確認する
