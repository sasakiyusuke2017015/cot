2. 章別カンペ（講師用）

各章を教えるときのねらい・つまずきポイント・投げかける質問。生徒向けページには出ません。

章 ねらい つまずき・見るところ 問いかけ
1. HTML
2コマ
 タグで構造を書く感覚をつかませる。見た目の話はまだしない。 見た目を整えたがるので「それは次章」と切る。閉じタグ忘れは自分で気付かせる。 「なぜここは div ではなく h1 にした？」
2. CSS
3コマ
 セレクタで要素を選ぶ感覚と、Flexboxで並べる感覚。 レイアウト崩れは必ず起きる。開発者ツールでボックスモデルを見せて自力で直させる。 「この余白は padding と margin どっちが正しい？」
3. JavaScript
6コマ
 エラーとの付き合い方を覚える章。文法より「エラー文→仮説→調査→修正」を体験させる。 詰まる人が一番多い。ここで30分ルールを本格的に運用開始する。答えを言わずコンソールを見せる。 「console.log を入れるならどこ？なぜそこ？」
4. Git
20コマ
 Gitの5コマンド習得は前半のみ。本体は「2人でオセロを完成させる」共同開発の体験。機能分解→分担→進捗管理を回させる。 機能分解を代わりにやらないこと。粗くても自分たちで割らせる。裏返し判定で必ず詰まるので、答えではなく「8方向をどう表現するか」だけ示す。コンフリクトは事故ではないと繰り返し伝える。 「いま何が動いていて、次に何を作る？その機能は1日で終わる大きさ？」
5. Python
6コマ
 「JSと似ているが別物」を体感させる。文法の暗記ではなく、JSで書けるものをPythonで書き直させるのが早い。 インデントでブロックを表すのが最初の関門。エラーが出たら行頭の空白を疑わせる。JSの癖（セミコロン・波括弧）が出るのは自然なこと。 「同じ処理をJSで書くとどうなる？どこが違う？」
6. SQL
6コマ
 テーブル設計ができること。SELECT/INSERT/UPDATE/DELETE と JOIN を、戦績データという具体で覚えさせる。 設計を代わりにやらないこと。「1行が何を表すか」を必ず自分の言葉で言わせる。最初は列が足りない設計を作りがちだが、後で気付かせるほうが学びが深い。 「この表の1行は何を表している？後から「対戦した日時で並べたい」と言われたら足せる？」
7. API
8コマ
 ブラウザとサーバが別プログラムだと腹落ちさせる。FastAPIで自分の手でエンドポイントを作らせ、オセロから実際に叩かせる。 通信が失敗すると想像で直そうとする。必ずNetworkタブと自動ドキュメント（/docs）を開かせて事実を見せる。CORSで詰まるのは通過儀礼なので、原因を説明してから直させる。 「いまリクエストは飛んでる？何が返ってきた？サーバ側とブラウザ側、どっちで落ちてる？」
8. DB連携
6コマ
 「再起動しても消えない」を体験させる。3層（ブラウザ→API→DB）の絵を自分で描けるようにする。 ORMから入りたがるが、まず生SQLで動かしてからORMに移らせる。SQLインジェクションは必ず実演して見せる（文字列連結の危険さは言葉だけでは伝わらない）。 「いまデータはどこにある？サーバを再起動したらどうなる？」
9. デプロイ
3コマ
 公開URLを人に渡すところまで。「動くものを世界に出した」経験が次の燃料になる。 公開前に環境変数・秘密情報のチェックを一緒にやる。ここは講師が必ず確認する。 「このリポジトリ、いま公開して困るものは入ってない？」
10. TypeScript
4コマ
 完成したオセロを型付きに直させる。動くものがある状態なので型の効果が見えやすい。 型エラーの文面に怯む。長いエラーも「何が」「どの型と」合わないかだけ読めばよいと教える。 「この関数、引数に何が来たら壊れる？」
11. React
8コマ
 オセロをReactで作り直させる。素のJSとの差分で「Reactが何を楽にするか」を語らせる。 DOMを直接触ろうとしたら止める。まず画面を部品に分解させてから書き始めさせる。 「この画面はどんな部品に分けられる？その部品に何を渡す？」

3. 基本理念

重要なのは「知識量」ではなく「問題解決能力」への移行。実務では検索・AI・ドキュメントを見ながら開発するため、文法暗記よりも次のサイクルを体で覚えることを最優先にする。

エラー文を読む→ 原因の仮説を立てる→ 調査する→ 修正する

5. 教師（メンター）の役割

この条件での教師は「講師」ではなくメンター兼コードレビュアー。知識を教えるのではなく、学習を設計・継続させる。

① 学習の道筋を作る 最重要

何をどの順番で学ぶかを設計し、迷わず進めるロードマップを示す。

② エラー解決の考え方を教える

答えを教えるのではなく「エラーを読む → 原因を予想 → どこを調べるか → 仮説を検証」を身につけさせる。

③ コードレビュー

毎回レビューするだけで成長速度が変わる。見るのは 命名 / 可読性 / 重複 / 責務の分離 / バグになりそうな箇所。

④ モチベーション管理

小さな目標を設定し、できたことを確認する。難しすぎる課題は出さない。

⑤ 「なぜ？」を問いかける

「なぜこの書き方にした？」「他の方法は？」「もし100件データがあったら？」——考えさせる質問で理解を深める。

🚫 教師がやらなくていいこと（書籍・動画・AIで代替できる）

文法を延々と講義する ／ スライドを読むだけ ／ 完成したコードを配る ／ すべて答えを教える

6. 質問のルール「30分ルール」

「分からなかったら聞いて」では質問する力が育たない。代わりにこう教える。

30分調べて、「分かったこと」「試したこと」「仮説」を持って聞く。

質問が具体的になり、調べる力・整理する力が同時に育つ。

7. 育成の3ステップ

STEP 1｜基礎理解 （1〜2週間）— コードが読める状態にする

  • 開発環境構築: VS Code / Git / ターミナル操作
  • プログラミング基礎: 変数 / 条件分岐 / 繰り返し / 関数 / 配列 / クラス
  • デバッグ方法: エラー文を読む / ログを見る

STEP 2｜小さい成果物を作る （2〜4週間）— 開発感覚をつける

初級

TODOアプリ / 電卓 / CSV集計ツール / 簡単なWeb API

中級

ログイン機能 / DB CRUD / ファイルアップロード / 外部API連携

完成度より「なぜこの設計にしたのか」を説明できることを重視する。

STEP 3｜実務形式へ移行 — チーム開発を経験する

  • Git: branch / commit / pull request / merge
  • コードレビュー: 命名 / 重複 / 責務分離 / エラー処理 / セキュリティ
仕様確認→設計→実装→テスト→レビュー→リリース

8. やってはいけないこと

❌ 最初から大きなシステム

新人は全体像が見えず混乱する。小さく作って積み上げる。

❌ 「分からなかったら聞いて」

質問方法が育たない。→ 30分ルールを教える。

❌ 文法暗記中心

実務では検索・AI・ドキュメントを見る。知識量より問題解決能力。

9. 伸びる人・伸びにくい人

🌱 伸びる新人

  • エラーを怖がらない
  • 仮説を立てる
  • 調べた内容を整理できる
  • 質問が具体的
  • 他人のコードを読む努力をする

🥀 伸びにくい新人

  • 答えを待つ
  • 動けばOKで済ませる
  • なぜ動くか説明できない

10. 毎回まわすサイクル

ゴールを明確にする→ 学ぶ内容を整理する→ 詰まったときの考え方を示す→ レビューで改善点を伝える→ 次回までの宿題を設定する

このサイクルを回せれば、限られた時間でも着実に力が伸びる。
